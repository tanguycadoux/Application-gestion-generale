# Architecture

Ce document décrit l'organisation du code et les décisions structurantes du projet, avec leur raison. Le fonctionnement côté utilisateur (format des notes, tâches issues des notes…) est décrit dans le [README](../README.md) ; le suivi des évolutions se fait dans les [issues](https://github.com/tanguycadoux/Application-gestion-generale/issues) GitHub.

## Contexte

- Application **locale et mono-utilisateur** : pas d'authentification, réglages Django non durcis (`DEBUG`, `SECRET_KEY` en dur).
- Django, SQLite, rendu côté serveur. Front sans Node ; seule étape de build, la feuille Tailwind (voir la section Front).

## Front

- Rendu côté serveur par les gabarits Django ; pas d'étape de build JS.
- **Tailwind CSS** v4 pour le style, **Material Symbols Rounded** en SVG inline pour les icônes, **htmx** pour les mises à jour partielles. Le détail des versions et des points de chargement est dans le README.
- **Aucune ressource externe** (#217) : les notes sont privées, et le navigateur ne doit contacter aucun serveur tiers. La feuille Tailwind est compilée en local par `django-tailwind-cli` (CLI autonome de Tailwind, version épinglée par `TAILWIND_CLI_VERSION`, sans Node) depuis `assets/css/source.css`, dans `static/css/tailwind.css`, non versionnée ; la CI la construit dans un job à part. htmx est embarqué dans `static/vendor/htmx/`, avec sa licence et un README (source, empreinte d'intégrité), et chargé une fois par le gabarit de base. KaTeX (#99) est embarqué de la même façon dans `static/vendor/katex/`, chargé par le gabarit de base des notes. Une bibliothèque front s'ajoute de la même façon (CodeMirror, #89). Le téléchargement du CLI de Tailwind est une étape d'installation, pas une requête de l'application. Les icônes (#218) sont des fichiers SVG de Material Symbols (`static/icons/`, licence et README dans le dossier), téléchargés une fois par `python manage.py add_icon` et recopiés dans les pages par `{% icon %}` (`core/icons.py`) : pas de police chargée. Les toasts sont rendus par le serveur (`{% icon %}` dans leur gabarit) ; ceux que crée un script sont les clones de `<template>` du gabarit de base. Garde-fous : un test refuse toute ressource externe dans les pages et les gabarits (hors contenu des notes), et le lanceur de tests (`app_gestion/test_runner.py`) fait échouer toute connexion réseau.
- **Fichier de log** (#468) : `LOGGING` écrit, en plus de la console, dans `logs/app.log` (rotation : 2 Mo, 5 anciens fichiers ; non versionné), ou dans le dossier de la variable d'environnement `APP_GESTION_LOG_DIR`. `INFO` pour les apps, `WARNING` pour `django.request` (4xx et 5xx). Les notes sont privées : le log n'en contient pas le texte. Les tests n'y écrivent pas (`test_runner.py`).
- **Adresses des fichiers statiques** (#469) : `?v=<empreinte du contenu>` suit chaque adresse, pour qu'après une mise à jour le navigateur ne garde pas un ancien script devant une page neuve. C'est le stockage (`VersionedStaticFilesStorage`, réglage `STORAGES`) qui l'ajoute : `{% static %}` et `static()` suffisent, il n'y a rien à écrire dans un gabarit. L'empreinte n'est recalculée que si le fichier change (date, taille) ; un fichier absent (Tailwind pas construite) garde son adresse nue. `ManifestStaticFilesStorage` est écarté : l'application tourne en local, avec `DEBUG`, sans `collectstatic`. Un module importé par `./x.js` n'a pas d'adresse dans un gabarit : l'import map de la page renvoie son adresse nue vers celle qui porte l'empreinte (`{% codemirror_importmap 'app/script.js' %}`, ou `{% modules_importmap 'app/script.js' %}` sans CodeMirror), les imports étant suivis depuis le script donné. Une page dont le script en module importe un autre de nos fichiers place donc l'une des deux balises avant ce script. Les tests comparent une adresse à `static(…)`, pas à une chaîne.
- Règle de style : tout en classes Tailwind (#79) ; CSS propre réservé à ce que Tailwind ne couvre pas : le HTML produit par le Markdown (`.rendered-content`, callouts) et les animations de la popover de colonne, créée en JavaScript (bloc `@layer components` de `assets/css/source.css`). Les toasts sont du HTML rendu par le serveur, en classes Tailwind (#293). Les confirmations ne passent plus par le script : popover HTML native du composant `confirm_button` (#292). Le détail est dans le README. Les éléments d'interface récurrents sont des composants partagés : balises d'inclusion de `core/templatetags/ui.py` (`{% load ui %}`), gabarits dans `core/templates/core/components/` (principes dans la section « Composants d'interface » plus bas). Le thème Tailwind (couleurs de Tailwind, toutes émises par `theme(static)`) et les styles de base sont dans `assets/css/source.css`.

## Apps et dépendances

```
app_gestion/   configuration : settings, urls, lanceur de tests sans réseau
core/          éléments communs : Project, Section, Tag, AppError, accueil,
               page Projets, gabarit de base, composants d'interface,
               calendrier mensuel, icônes, validateur HTML
images/        modèle Image, import et suppression des images
note_taking/   notes, analyse qmd, rendu, import et export, recherche,
               calendrier des notes, pages d'images
todolist/      tâches : arbre, avancement, calendrier, frise, tâches issues des notes
```

Sens des dépendances (une flèche signifie « importe ») :

```
todolist ──► note_taking ──► images ──► core
   │              │                      ▲
   └──────────────┴──────────────────────┘
```

- `core` ne dépend d'aucune app (#179). Ce qu'il affiche des autres apps, chacune le déclare dans son `AppConfig`, et `core/app_registry.py` le lit dans l'ordre d'`INSTALLED_APPS` :
  - `nav_section` : sa section du menu commun (`NavSection` : titre, rang, `NavItem` de nom d'URL, libellé et icône), lue par le processeur de contexte `core.context_processors.navigation` ;
  - `debug_pages` : ses pages réservées au mode DEBUG (#235), réunies par `nav_sections()` dans une dernière section « Debug » du menu, **seulement si `settings.DEBUG`** ;
  - `dashboard_blocks` : ses blocs de l'accueil général (#233), des `DashboardBlock` (titre, rang, gabarit, fonction de contexte) que `core.views.index` rend dans l'ordre, sans savoir ce qu'ils montrent : « Note du jour » (`note_taking/dashboard.py`), « Tâches à échéance proche » et « À traiter » (`todolist/dashboard.py`) ;
  - `project_blocks` : ses blocs de la fiche d'un projet (#205), des `ProjectBlock` (ancre, titre, rang, gabarit, fonction de contexte) que `core.views.project_detail` rend dans l'ordre (voir « Fiche d'un projet ») ;
  - `project_usages` : ce qui utilise un projet chez elle (chemin de comptage depuis `Project`, libellés), pour l'afficher dans la liste des projets et refuser la suppression d'un projet utilisé. On compte des notes, pas des passages : c'est pourquoi le chemin est déclaré plutôt que déduit des relations du modèle.
- `images` ne connaît pas les notes : c'est `note_taking` qui référence les images. L'app reste ainsi utilisable par un futur éditeur d'images.
- `note_taking` ne connaît pas les tâches (#179). Après le recalcul des passages d'une note, elle émet le signal `passages_processed` (`note_taking/signals.py`), dans la même transaction ; `todolist` l'écoute (`todolist/receivers.py`) et crée les tâches. `todolist` dépend donc de `note_taking` : le signal, `Passage`, et `Note` pour le lien vers la note d'origine d'une tâche. Pour proposer une suite à l'enregistrement (#239), un receveur renvoie un `NoteFollowUp` (libellé et adresse, construite par l'app qui l'écoute) ; `process_passages` les range dans `note.follow_ups`, et la note redirige vers la première ou les cite dans le compte rendu d'import, sans connaître l'app qui les propose.
- Ce sens est vérifié par un test (`core/tests/test_dependencies.py`) : imports Python et noms d'URL cités dans les gabarits, hors tests et migrations.

## Adresses (#236, #273)

- Tout en anglais, un préfixe par domaine : `/notes/`, `/tasks/`, `/projects/`, `/images/` (les chemins des projets sous `/projects/<id>/paths/`, leurs suggestions sous `/paths/`). Les collections sont au pluriel, l'action est en fin de chemin (`/notes/<AAAA-MM-JJ>/edit/`), le `/` final est partout, les mots composés se séparent par des tirets. Le tableau des notes est `/notes/list/`, le calendrier `/notes/`.
- Les paramètres de requête sont en anglais aussi : `month` (`AAAA-MM`), `name`, `project`, `path`, `headings`, `q`, `sort`, `direction`.
- **Une note s'adresse par sa date**, au format ISO (`/notes/2026-07-21/`), seule adresse qui fait foi, actions comprises (`edit`, `delete`, `export`, `source`) ; l'analyse JSON est sous `/debug/` (voir « Pages de développement »). Le convertisseur `date` (`core/converters.py`) refuse une date impossible : 404. L'adresse par id (`/notes/<id>/`, `/notes/<id>/edit/`, et les anciennes `/note_taking/note/<id>/…`) redirige vers elle par une redirection permanente qui garde la méthode (308). Changer la date d'une note change son adresse : l'enregistrement redirige vers la nouvelle, et l'ancienne mène à « introuvable ».
- Les adresses se construisent par `{% url %}` / `reverse`, jamais à la main ; une note se passe par sa date (`args=[note.date]`).

## Menu commun (#232)

Un seul menu pour toute l'application, dans `core/templates/base.html` : une section par app (Notes, Tâches, Projets), rangées par le `order` de leur `NavSection`, déclarée dans l'`AppConfig` (voir « Apps et dépendances »). La page courante est marquée par `nav_link` (`aria-current="page"`). Aucun gabarit d'app ne déclare de menu : ajouter une page se fait dans l'`AppConfig`.

- **Largeur fixe** (`w-60`), donc la page ne se décale plus d'une app à l'autre.
- **Replié en icônes** : le bouton du bas pose `data-collapsed` sur `<nav>` (`nav.js`) ; les libellés et les titres de section se masquent par des variantes `group-data-collapsed/nav:` de Tailwind, sans règle CSS propre. Chaque lien garde son libellé en `aria-label` et en infobulle (`title`). Le bouton, `hidden` dans le HTML, ne s'affiche que si le script s'exécute (`aria-expanded`, libellé « Replier / Déplier le menu »). Le script est chargé sans `defer`, juste après le menu, pour poser l'état avant le premier affichage.
- **État retenu** dans `localStorage` (`main-nav-collapsed`), dans un `try/catch` : sans stockage, le menu fonctionne et repart déplié.
- **En-tête général** (#355) : un `<header>` sur toute la largeur (`col-span-2`), au-dessus du menu et du contenu, après le lien d'évitement. La grille de `<body>` a deux lignes (`grid-rows-[auto_minmax(0,1fr)]`, hauteur d'écran) : l'en-tête, puis le menu et `<main>`, dont seul le contenu défile. L'en-tête est une grille de trois colonnes `1fr / 36rem au plus / 1fr` : à gauche le **nom de l'application** (« Gestion générale », lien vers l'accueil, `title="Accueil"`) : il se comporte comme un logo, sans fond ni survol, identique sur l'accueil (pas de `aria-current`) ; l'accueil a quitté le menu (#360), au centre la barre de recherche, à droite un emplacement vide (`#header-end`, bloc `header_end`) pour plus tard. Sa **hauteur est fixe** (`h-13`, #370) : sans elle, l'en-tête de la page de recherche, qui vide le bloc `menu_search`, prenait la hauteur du seul nom de l'application, et le nom, le menu et le titre remontaient de 6 px en y arrivant. Le nom reste sur une ligne (`whitespace-nowrap`) : passé à la ligne sur un écran étroit, il dépasserait de cette hauteur. Les pages ont leur propre `<header>` dans `<main>` : « l'en-tête de la page » dans les tests est celui de `<main>`.
- **Barre de recherche** (#202, #355 ; modèle : `research-paper-relationship-graph`) : au centre de l'en-tête, un `<search>` qui contient un vrai `<form method="get">` vers la page de recherche, champ `q` : elle marche sans JavaScript, et reste visible menu replié. La page vient de l'`AppConfig` (`search_page`, un `NavItem`, lu par `app_registry.search_page()` et le processeur de contexte `nav_search`) : `core` n'écrit aucun nom d'URL d'une app. `search.js` (chargé avec `defer`) fait de **Ctrl+K** (⌘K sur Mac, où l'indice devient « ⌘ K ») le raccourci : il met le curseur dans la barre, ou, sur la page de recherche, dans sa zone de texte (`input[type=search][name=q]`). La page de recherche, qui a sa propre zone, vide le bloc `menu_search` de `base.html`. L'entrée « Recherche de notes » est aussi dans la section Notes du menu (#360) : la barre ne suffit pas pour aller filtrer par chemins.
- **Raccourcis clavier** : tout `<kbd>` (balise `{% kbd %}`, indice « Ctrl K » de la barre) est en police à chasse fixe (`font-mono`).
- Pas de version mobile (choix de l'utilisateur).

## Accueil général (#233)

Un tableau de bord, un `<section>` nommé par bloc (`aria-labelledby`), sur deux colonnes à partir de `lg`. Les blocs viennent des apps (voir « Apps et dépendances ») : `core` appelle la fonction de contexte de chacun et rend son gabarit, comme `home_link` le faisait pour l'ancien menu d'accueil.

- **Note du jour** : la date, puis « Ouvrir la note du jour » si elle existe, « Créer la note du jour » (formulaire prérempli à la date) sinon.
- **Tâches à échéance proche** : les tâches en cours dont l'échéance est passée ou à moins de `SOON_DAYS` jours (le seuil du signal `soon`), les plus en retard d'abord, **dix au plus** puis « et N autres » : un retard accumulé n'envahit pas l'accueil. Chaque ligne : titre (deux lignes au plus, titre complet en infobulle), pastille du projet, temps restant coloré comme dans la liste. Les tâches écartées sont exclues (`Task.objects`).
- **À traiter** (#384, `pending`) : un rappel de ce qu'on a noté vite, pas un blocage. Quatre rubriques, chacune avec son compte, montrée seulement si elle a quelque chose, la plus ancienne d'abord, **dix lignes au plus** puis « et N autres » : les tâches à revoir **par note** (`note_review`, « dont N sans projet ») ; les tâches en cours **sans échéance**, ni déclarée voulue (`Task.no_due_date`), ni à revoir (le bilan règle leur échéance), vers la liste filtrée (`?due=none`, le même critère que `task_table.undated`) ; les notes qui ont du **texte sans projet** (#385), vers la recherche « Sans projet » (`?no_project=on`) ; les **tâches sans projet** hors bilan (une case du texte sans projet reste à revoir tant qu'on ne lui a pas choisi de projet : elle est dans la première rubrique). Sans rien à traiter : « Rien à traiter. ». `todolist` le déclare, car il lit les notes (`todolist` importe `note_taking`). `Task.no_due_date` se coche dans le formulaire de la tâche et retombe dès qu'une échéance est donnée (`Task.save`).
- Pas de « dernières notes » ni d'accès aux projets : le menu commun suffit (choix de l'utilisateur).
- **Bilan de la semaine** (#208), relié depuis l'accueil : `/week/` (semaine en cours) et `/week/2026-W48/` (convertisseur `week`, `core/weeks.py` : numéro et année ISO ; une semaine impossible est un 404), avec semaine précédente et suivante. Comme l'accueil, `core` rend les blocs que les apps déclarent (`week_blocks`, `WeekBlock`, dont le contexte reçoit la `Week`) ; le résumé de l'assistant (M18) en sera un de plus. **Notes** (`note_taking/week.py`) : par projet (texte sans projet et notes vides à la fin), chaque note avec les chemins qu'elle y écrit, liés à leur titre. **Tâches** (`todolist/week.py`) : terminées (`completed_at`) et créées (`created_at`) entre le lundi et le lundi suivant à minuit, **heure locale** ; en retard **à la fin de la semaine** pour une semaine passée (échéance au plus tard le dimanche, déjà créée, pas terminée ce dimanche-là, même si elle l'est depuis), **aujourd'hui** pour la semaine en cours, sans objet pour une semaine à venir. L'échéance est celle d'aujourd'hui : ses changements ne sont pas gardés ; une tâche décochée perd sa date de complétion ; les écartées sont exclues.

## Pages de développement (#235, #156)

Une section « Debug » du menu, dernière, **visible seulement avec `DEBUG = True`** : elle réunit les `debug_pages` des `AppConfig`.

- **Les adresses n'existent pas sans `DEBUG`** : elles sont ajoutées à `urlpatterns` sous `if settings.DEBUG:` (`core/urls.py`, `note_taking/urls.py`) ; leurs vues refusent aussi (404) hors `DEBUG`, au cas où elles seraient branchées autrement. Elles vivent sous `/debug/`.
- **Galerie des alertes** (`/debug/alerts/`, #156) : un toast par niveau et un message long, rendus par le serveur (`{% message_toast %}`) mais gardés affichés (`alerts_gallery.js` retire `data-toast-autohide`) ; deux boutons qui créent un toast par script (`Toast.show`, un succès qui disparaît après 6 s et une erreur qui reste) ; et la popover native de `confirm_button`, ouverte au chargement. Pour juger le rendu sans déclencher de vrais messages.
- **Analyse JSON d'une note** (`/debug/notes/<AAAA-MM-JJ>/json/`, `note_taking:note_json`) : retirée de la page de la note ; une page de choix de la date (`/debug/notes/json/`) y mène.
- **Tester** : `core/tests/debug_urls.py` fournit `DebugUrlsTestCase`, qui active `DEBUG` le temps de la classe et recharge les modules d'adresses (le lanceur de tests force `DEBUG = False`, donc les adresses de debug n'y existent pas) ; `core/tests/test_debug.py` vérifie l'absence (404, `NoReverseMatch`, pas de section dans le menu) et la présence.

## Tableaux triés et filtrés (#178)

Un seul mécanisme pour les tableaux de toutes les apps, calqué sur `research-paper-relationship-graph` : **côté serveur, dans l'URL**. La page se partage, fonctionne sans JavaScript, et tout le tableau est trié et filtré, pas seulement ce qui est affiché. `core/tables.py` ne connaît aucune app.

- **Tri** : `?sort=date` (croissant), `?sort=-date` (décroissant). `Sorting` déclare les colonnes (`Column` : une expression pour un queryset, ou une clé pour une liste Python), le tri par défaut et les égalités, toujours départagées dans le même ordre jusqu'à `pk`. Les lignes sans valeur restent à la fin dans les deux sens. Un clic sur la colonne triée inverse le sens ; un clic sur une autre colonne commence par son sens naturel (`descending_first`). Un tri inconnu revient au tri par défaut. `Sorting.apply` trie un queryset, `Sorting.sort_items` une liste Python (tableau arborescent).
- **Filtre en arbre** (#302) : `PathTreeFilter` prend deux paramètres répétés (projet, niveau) et une fonction `tree(projets, niveaux)` qui rend les nœuds de `core.path_tree` avec leurs compteurs (l'appelant les fournit) ; valeur lue = (clés des projets, identifiants des niveaux), les valeurs inconnues de la base sont ignorées. Le panneau l'affiche avec `{% path_tree %}` en cases, le résumé donne une puce par choix.
- **Filtres** : `Filters` range les filtres par colonne, une colonne pouvant en porter plusieurs dans le même panneau. Types : `TextFilter` (contient), `ChoiceFilter` (un choix, avec une valeur par défaut qui n'est pas un filtre actif ; des radios, ou un `<select>` au-delà de six choix, sauf pour des projets, qui gardent leur pastille), `MultiChoiceFilter` (plusieurs choix à cocher, réunis par « ou » ; le paramètre est **répété** dans l'URL, `?project=A&project=B`, aucune case cochée n'est pas un filtre ; valeurs inconnues et doublons ignorés ; générique : projets aujourd'hui, chemins ou tags plus tard), `DateRangeFilter` (`<clé>_from`, `<clé>_to`, AAAA-MM-JJ, bornes inversées remises dans l'ordre, date mal écrite signalée sans bloquer l'autre borne). Chaque filtre lit ses paramètres (`?project=ASTERICS&date_from=2025-11-01`) et porte la fonction qui l'applique à ce que la page filtre ; `Filters.read` donne les filtres actifs et leurs erreurs de saisie, `Filters.apply` les applique.
- **Composants** : `{% column_header "Date" "date" classes="…" %}` rend l'en-tête (`<th>`, lien de tri avec `aria-sort` et flèche, entonnoir) à partir de `sorting`, `sort`, `filters` et `active_filters` du contexte de la page ; `{% filter_summary %}` liste les filtres actifs au-dessus du tableau, chacun retiré d'un clic (un filtre à choix multiples donne une pastille par valeur cochée, avec la pastille du projet, qui retire cette seule valeur), avec les erreurs de saisie. L'entonnoir ouvre une **popover HTML native** sans JavaScript, ancrée à son bouton par l'ancrage CSS (`.table-filter-popover`, `assets/css/source.css`, comme `.confirm-popover`). Le formulaire d'une colonne reprend le tri et les autres filtres en champs cachés ; tout changement de tri ou de filtre repart de la première page. L'entonnoir d'un filtre actif est bleu et annoncé (`filtre actif`). Un tableau filtré sans résultat reste affiché, pour changer les filtres.
- **Liste repliable et recherche d'un filtre à choix multiples** (`column_header.html`, `core/static/core/table_filters.js`, chargé par le gabarit de base) : les cases sont dans un **`<details>` natif**, replié par défaut et **ouvert d'office dès qu'un choix est coché**, dont le résumé donne le compte (« Projets (2 sur 7) ») ; aucune zone n'a de barre de défilement, ni la liste, ni le panneau, qui s'étend à son contenu (la popover garde seulement le `overflow` par défaut du navigateur, sans effet tant qu'elle tient dans l'écran). Le champ de recherche est **hors du `<details>`**, donc toujours visible, sans marge (aligné sur les autres champs) : aucun conteneur du panneau ne rogne son contour de focus. Amélioration progressive : sans JavaScript, le champ de recherche reste caché (`hidden`) et les cases sont accessibles en ouvrant la liste ; le filtre marche. Avec le script, le champ apparaît, a le focus à l'ouverture de la popover (`autofocus`, posé sur le premier champ de saisie du panneau, jamais sur des boutons radio), **taper ouvre la liste** et masque les cases qui ne correspondent pas (casse et accents ignorés, `normalize("NFD")`) ; une case **cochée n'est jamais masquée**, « Aucun projet ne correspond. » s'affiche quand rien ne correspond, et le compte du résumé suit les clics. Entrée dans le champ n'envoie pas le formulaire.
- **Tableau des notes** (`note_taking/note_table.py`) : tri par date ; filtres « Date » (de, à) et « Projets » (un ou plusieurs des projets qui ont des notes, cases à cocher avec leur pastille ; les notes d'au moins un projet coché, une fois chacune). Le filtre par projet ne cache pas les autres projets d'une note (le préchargement est indépendant du filtre) ; l'export prend toutes les notes, filtrées ou non. La popover provisoire (`table.js`) a disparu.

## Modèle de données

```
Note ──< Passage  >── Project          (core, facultatif)
           │  │  └──── Section (option)  (core)
           │  └──<>── Tag              (core)
           └────<>─── Image            (images), via PassageImageLink

Task >── Project, Task >── Section (option), Task >─< Tag,
Section >── Project, Section >── Section (parent, option),
Task >── Task (parent, option)
```

- **`Note`** : une note par jour (`date` unique) ; `body` contient le texte de la note.
- **`Passage`** (#387) : une section de la note telle qu'écrite, le texte entre un titre et le suivant (ou depuis le début de la note), à sa place : rang dans la note (`position`), lignes de début et de fin dans `Note.body` (`start_line`, `end_line`), projet (facultatif : le texte avant le premier `#`, #385), section (la dernière du chemin, facultative) et tags, titres de la section (`heading_path`, #240) et leurs identifiants dans la page de la note (`heading_id` pour le sien, `anchor_path` pour tout le chemin). **Données dérivées** de `Note.body`.
- **`Project`, `Section`, `Tag`** : partagés par les notes et les tâches. Un projet a un nom unique, une couleur (#162) et une description. Une section est un niveau d'un chemin sous un projet (voir « Chemins sous un projet »).
- **`Task`** (tâche) : titre, projet, section (son sujet) et tags, description, priorité, échéance ; avancement en pourcentage (`progress`), état terminé (`done`) et moment où elle l'est devenue (`completed_at`), avancement d'avant la coche, rendu au décochage (`progress_before_done`, #237) ; parent optionnel, pour les sous-tâches. Une tâche issue d'une note garde la date, le chemin et le texte de sa ligne (`note_date`, `note_path`, `note_line_text`), et son état dans la note (`note_state` : à revoir, revue, gardée sans sa ligne, écartée, #240). `Task.objects` exclut les tâches écartées ; `Task.all_objects` les compte.
- **`Image`** : nom de fichier d'origine (unique, sert de référence dans les notes), fichier affiché, source éditable optionnelle.

## Décisions

### La base fait foi, le qmd est un format d'échange (#24)

`Note.body` est le texte de la note, **sans bloc d'en-tête** (`---` / `date: …` / `---`). La date est celle de `Note.date`. Le bloc d'en-tête n'est lu qu'à l'import (vérification de la date) et sera régénéré à l'export (#64). Dans le formulaire web, un bloc d'en-tête éventuel est retiré, ou refusé si sa date diffère.

On ne stocke pas la note sous forme structurée (arbre de sections) : le découpage en passages perd de l'information (origine des tags, mise en forme) et ne permet pas de régénérer la note. Le texte reste la source.

Export et import (#64, #114) : l'export produit une archive zip à la disposition d'un dossier Quarto (`AAAA-MM-JJ.qmd` à la racine, `images/<nom>`), qui forme un projet Quarto valide une fois dézippée ; chaque fichier est généré depuis la base (`note_taking/qmd/export.py`). Un seul formulaire d'import (`note_taking/importing.py`) accepte plusieurs fichiers et traite chacun selon son type : un `.zip` est l'archive de l'export, un `.qmd` une note, une image une image. Les images sont importées avant les notes, qui les citent. La base fait foi : une image déjà présente sous ce nom est gardée (le fichier importé est écarté, sans doublon, le nom étant unique) ; une note dont la date existe déjà n'est jamais remplacée sans confirmation : pour l'instant elle est ignorée et signalée dans le compte rendu (choix entre les deux versions : #115). Le remplacement volontaire d'une note par son fichier source reste sur la page de la note.

### Les passages sont dérivés et recalculés

`process_passages` supprime et recrée les passages d'une note, avec leurs liens (tags, images), à chaque enregistrement (import, mise à jour, formulaire), en tout ou rien (#221) : si l'analyse échoue, les passages et les tâches d'avant restent intacts, et le texte de la note, déjà enregistré, n'est pas annulé. Conséquences :

- aucune donnée saisie ne doit être rattachée à un passage, car elle serait perdue au prochain enregistrement ;
- **les passages sont un index, pas ce qu'on affiche** (#234) : la page d'une note rend `Note.body` en entier (`render_note_body`, `NoteDetail`), dans l'ordre écrit, texte d'avant le premier titre compris. Les blocs `{.metadata}` s'y affichent en pastilles (`render_metadata`, tags et `todo: true`). Les passages servent à la recherche, aux liens vers les images, aux tâches, aux liens entre notes (#207), à la fiche projet (#205), et plus tard à l'assistant. La vue « Markdown » a disparu : l'ancienne adresse par id mène à la note ;
- après une évolution du parseur, `python manage.py reprocess_notes` recalcule toutes les notes (`--dry-run` pour simuler).

**Passages à la place des note parts** (#387) : une note part réunissait toutes les lignes d'un même projet, chemin et tags, où qu'elles soient dans la note, sans leur place ; d'où une ancre de résultat menant à la première occurrence d'un titre répété (#201), une vue Document qui ne suivait pas l'ordre écrit, et aucune place pour le texte sans projet (#36). Un passage suit le texte : une ligne par section écrite, à sa place, avec ses lignes et l'identifiant de son titre. Le parseur (`NoteParser.new_passage`, `add_content`) ouvre un passage à chaque titre reconnu, et sous le même titre quand un bloc `{.metadata}` change les tags après du texte (la portée des blocs est inchangée) ; un passage vide (un titre suivi d'un sous-titre) est retiré, sa place comptant dans les lignes du passage d'avant. La migration `0042_passages` crée les tables, supprime les anciennes, recrée l'index plein texte, puis **recalcule elle-même les passages** (`reprocess_notes`) : par exception à la règle des migrations, elle appelle le code de l'application, l'analyse d'une note étant tout le parseur ; si ce code ne correspond plus au schéma (une base migrée bien plus tard), le recalcul est abandonné sans rien casser, et la migration demande de lancer `reprocess_notes`.

### « Passage » dans l'interface et dans le code (#362, #387)

L'utilisateur écrit des notes ; ce que la recherche trouve et que les compteurs comptent en est un morceau, un **passage**, mot plus parlant qu'« extrait » (déjà le nom de la vue de recherche et du texte surligné). Le modèle s'appelait `NotePart` (la réunion de toutes les lignes d'un même chemin, où qu'elles soient dans la note, sans leur place) ; #387 l'a remplacé par `Passage`, une section telle qu'écrite, qui correspond enfin à ce que l'utilisateur a écrit. On compte à la fois les passages et les notes, plutôt que les notes seules : le nombre de passages est celui des résultats affichés et des compteurs de l'arbre.

- **Où** : le décompte de la recherche (« 3 passages dans 2 notes », accordé au singulier), l'aide de la recherche (qui définit le passage : le texte d'une note sous un même titre, avec les mêmes tags, où tous les mots sont cherchés), les usages d'un niveau sur la page Chemins et dans le message d'une suppression refusée (`SectionUsage("passages", "passage", "passages")` de `note_taking`), le refus d'un renommage qui fusionnerait des passages (`NoteRenameError`), l'aide de `reprocess_notes`.
- **Compteurs de l'arbre** : le nombre reste celui des passages, affiché seul, « (12) », pour ne pas charger l'arbre ; `{% path_tree … count_noun="passage" %}` le nomme au survol (`title="12 passages"`) et pour les lecteurs d'écran (« passages » en `sr-only` dans les parenthèses, lu « 12 passages »). Comme la page Chemins écrit le mot, l'unité est aussi visible sans survol, une seule fois : sous la légende « Projets et chemins », `notes_search.html` affiche « Entre parenthèses : le nombre de passages, sous-niveaux compris. », seulement quand l'arbre a des nœuds. La ligne est chez l'appelant, pas dans le composant : elle dépend du formulaire autour de l'arbre. Sans `count_noun`, le compteur reste le nombre seul : c'est le cas de l'arbre des tâches, qui compte des tâches.
- **Noms du code** (#387) : `Passage`, `passages`, `search_passages`, `process_passages`, tables `passage_search` et `passage_vocab`, champs `note_date` et `note_line_text` des tâches. Les anciens noms ne restent que dans les migrations passées.
- **Garde-fou** : `core/tests/test_vocabulary.py` rend les pages visibles (projets, chemins, bilan d'un renommage, recherche et ses vues, note, tâches, bilan des tâches, compte rendu d'import, message de suppression) et lit les gabarits (hors commentaires et pages de debug), les scripts et les chaînes Python (hors docstrings, tests et migrations) : « note part » n'y est nulle part.

### Tâches issues des notes

Une case vide `- [ ] texte`, où qu'elle soit, donne une tâche ; dans une branche `todo: true`, chaque élément de liste en donne une (#297). Ces tâches sont créées par `todolist`, à l'écoute du signal `passages_processed` (voir « Apps et dépendances »).

- Le titre est le texte de la ligne sans son marqueur de liste ni sa case (#222). Une case cochée n'est pas une tâche : elle est ignorée (#297, qui remplace « une case cochée ne termine pas la tâche »), comme une ligne qui n'est pas un élément de liste ; les cases d'un bloc de code aussi (`lines_of`).
- Une ligne imbriquée sous un élément de liste, selon la règle des sous-listes du rendu (#229), donne une sous-tâche de la tâche la plus proche au-dessus (#238), sur plusieurs niveaux ; une ligne sans marqueur sous un élément, suite de son texte pour Pandoc, n'est pas une tâche. Le texte d'un élément parent, tâche ou non, entre dans le chemin de la ligne. Le parent n'est posé qu'à la création : il a pu être choisi à la main ensuite.
- La tâche reprend le projet et la section du passage. Ses tags sont ceux du passage, sans `TODO`. Une case du texte sans projet (#385) donne une tâche sans projet ni chemin, « à rattacher à un projet » (`Task.project` facultatif) : le bilan de la note propose son projet, et elle y reste à revoir tant qu'aucun n'est choisi ; sa fiche le signale, la liste la range sous « Sans projet ». Sa ligne rangée ensuite sous un titre, dans la note, la range aussi (#442), si on ne lui a pas déjà choisi de projet. C'est le plus simple : pas de projet réservé « À ranger », l'absence est la vérité des données et les affichages la traitent. Elle n'a pas d'échéance (#239) : la date de la note la mettait en retard dès le lendemain.
- **Identité** (#240) : une tâche générée est identifiée par la date de la note, le chemin de sa ligne et son texte, pas par une clé étrangère vers son passage, recréé à chaque enregistrement. Aucun receveur ne dépend du découpage en passages : les lignes d'une tâche, ses sous-tâches et le marqueur `todo: true` se lisent passage par passage, et la note part, qui réunissait les lignes d'un même chemin écrites à deux endroits, faisait d'une ligne indentée au début du second endroit une sous-tâche de la dernière ligne du premier, ce qu'un passage ne fait plus. Le chemin est fait des titres de la section tels qu'écrits, puis des éléments parents : « Test › BLABLA › P » pour la ligne « F » sous « P ». Une même ligne sous un autre sujet ou sous un autre parent est donc une autre tâche. Une tâche créée avant #240, sans chemin, est reprise par sa date et son texte au prochain enregistrement de sa note (`reprocess_notes` les reprend toutes).
- **Cycle de vie** (#240) : une tâche créée est **à revoir**. Tant qu'une note a des tâches à revoir, son enregistrement (formulaire, remplacement par le fichier source) redirige vers son bilan (`todolist:note_review`), et un import le cite dans son compte rendu. Le bilan se calcule depuis la base, sans session. Il présente :
  - les tâches dont la ligne est dans la note : échéance, priorité, projet et sujet ; enregistrer les rend **revues**, même sans échéance. « Plus tard » les laisse à revoir ;
  - les tâches dont la ligne a disparu (modifiée, déplacée ou retirée) : une tâche revue dans ce cas redevient à revoir. On la garde (**gardée sans sa ligne**, plus jamais présentée), on l'écarte, ou on la remplace par la tâche d'une nouvelle ligne : l'ancienne prend son chemin et son texte, garde avancement, échéance et sous-tâches, reçoit celles de la nouvelle, qui est supprimée. Son titre suit la ligne, sauf s'il a été renommé à la main ; son projet et son niveau aussi, s'ils étaient ceux des titres de son ancienne ligne (`placed_by_note`), sauf vers le texte sans projet : un chemin choisi à la main est gardé. Un niveau que plus rien n'utilise est alors oublié. **Même texte** (#382) : une nouvelle tâche dont le texte est le même (casse et blancs ignorés, `same_text`) est choisie d'avance en remplacement (`same_text_replacements`, appelée par `BaseGoneLineFormSet.get_form_kwargs`) ; chacune n'est proposée qu'une fois, et entre plusieurs, celle dont le chemin a le plus de niveaux communs avec l'ancien, à la fin puis au début. Sous la tâche, l'ancien chemin et celui de la tâche proposée, les niveaux changés en gras (`path_changes` : à même profondeur, niveau par niveau ; sinon, ce qui reste commun au début et à la fin n'a pas changé). Un titre renommé dans l'éditeur n'est pas reconnu à l'enregistrement, contrairement au renommage de la page Chemins : le bilan montre ce qui bouge, et le choix proposé évite le doublon.
- **Tâche écartée** (#240, #290) : retirer une tâche dont l'arbre (elle et ses sous-tâches) contient une tâche issue d'une note écarte l'arbre en entier, tâches saisies à la main comprises, pour que le rétablir le rende intact (`remove_task`) ; la page de la tâche dit alors « Écarter » au lieu de « Supprimer » (`removal_dismisses`). Un arbre saisi à la main est supprimé ; une tâche déjà écartée qu'il portait est détachée. Une tâche écartée n'est plus affichée nulle part (`Task.objects` l'exclut : listes, sous-tâches, avancement du parent, formulaires) ni comptée dans les usages d'un projet (`ProjectUsage.exclude`), et le prochain enregistrement de la note ne la recrée pas. Un projet utilisé seulement par des tâches écartées se supprime avec elles (`protect_unless_dismissed`).
- **Rétablir** (#290) : la liste des tâches a un état « Écartées » (`?state=dismissed`, #294), un tableau à part avec une ligne par tâche écartée dont le parent ne l'est pas (`dismissed_rows`), ses filtres s'appliquant aussi à ces lignes ; la liste en cours renvoie vers lui par un lien qui compte les écartées (`top_dismissed`). « Rétablir » (`restore_task`) rétablit aussi ses sous-tâches écartées, ce que la confirmation et le message disent. Chacune redevient revue si sa ligne est encore dans sa note, gardée sans sa ligne sinon ; une tâche saisie à la main le redevient. La tâche retrouve son parent s'il est encore affiché ; s'il est écarté, elle revient à la racine, et le message le signale. Pas de suppression définitive : la ligne, si elle est encore dans la note, reviendrait en tâche au prochain enregistrement, ce que l'écart sert justement à empêcher.

### Avancement, état terminé et incohérences des tâches (#164, #165)

- L'avancement d'une tâche sans sous-tâche se saisit, et elle est terminée à 100 %. Celui d'un parent se calcule : c'est la moyenne arrondie de ses enfants, propagée aux ancêtres à chaque enregistrement.
- Un parent se coche à la main. Il se décoche dès qu'un de ses enfants n'est plus terminé. À 100 % et non coché, il est « à valider ».
- Les écarts entre une tâche et ses sous-tâches ne sont pas empêchés mais signalés, des deux côtés : échéance d'une sous-tâche après celle du parent, projet différent. Seule une boucle parent-enfant est refusée.
- Supprimer une tâche supprime ses sous-tâches ; la confirmation et le message le disent (#223).
- Une seule règle d'urgence, `Task.due_signal` : terminée, en retard, proche (sous 3 jours) ou normale (#189).

### Projets, sections et tags partagés (#19, #20, #295)

- Un même modèle pour les notes et les tâches, fusionnés par nom lors de la migration.
- Une **section appartient à un projet** (#295) : « Calcul thermique » sous deux projets est deux sections. Elle remplace le sujet, qui était global ; voir « Chemins sous un projet ».
- Un nom de projet ignore la casse (#374), comme un niveau : `project_for` (`core/projects.py`) retrouve « Chantier Nord » pour `# chantier nord`, en Python ; la contrainte `unique_project_name_ci` (`LOWER`, ASCII seulement) est un filet, et le formulaire de création refuse un nom pris à la casse près. La migration `core/0009_merge_projects_by_case` a réuni les projets existants de même nom à la casse près : le plus utilisé (passages et tâches) est gardé, à égalité le plus ancien ; ses premiers niveaux homonymes sont réunis (comme `merge_section`), les autres passent sous lui. Les tags respectent la casse.
- Un tag devenu inutilisé reste en base, mais n'est pas proposé dans la recherche. Une section que plus rien n'utilise est supprimée à l'enregistrement d'une note (`forget_unused_sections`).
- Les tags vides (`tags: []`) sont ignorés.

### Chemins sous un projet (#287, #295)

Un chemin est une suite de niveaux sous un projet : « Réunion › Préparation ». C'est un **arbre de lignes** (`Section` : projet, parent facultatif, nom), pas un texte à séparateurs : un « / » dans un titre (« Rapport RT17/A ») ne peut pas passer pour un séparateur, et renommer un niveau fait suivre ses descendants. Modèle repris des tags hiérarchiques de `research-paper-relationship-graph`, avec les parents comme vraies lignes.

- Un niveau est **unique sous son parent, casse ignorée** ; un niveau déjà connu garde la casse de sa première écriture (`section_for`). Le `LOWER` de SQLite ne replie que l'ASCII : la comparaison complète se fait en Python, les contraintes de la base sont un filet.
- Le séparateur n'existe qu'à la **saisie** (« / » entre niveaux, « // » pour un « / » littéral : `split_path`, `join_path`) et à l'**affichage** (« › »). Les notes ne passent pas par ce texte : leurs titres donnent directement les niveaux.
- Supprimer un niveau supprime ses descendants. `Section.project` est en cascade ; `Passage.section` est protégé, `Task.section` passe à vide.
- `core` ne connaît aucune app : `forget_unused_sections` lit les clés étrangères qui mènent à `Section` sur le modèle, sans importer les apps.
- **Dans les notes** (#296) : `#` donne le projet, `##` à `######` les niveaux du chemin, sans limite de profondeur (`NoteParser.current_path`). Les titres ne donnent plus de tags : seuls les blocs `{.metadata}` en donnent, avec une portée sur la branche, jamais un niveau. `heading_path` garde tous les titres tels qu'écrits, dont dépend l'identité des tâches (#240). Le **nom d'un niveau** est le texte du titre **sans ses attributs** Pandoc (#367, `heading_name`, même règle que l'affichage des résultats, #356) : deux titres qui ne diffèrent que par leurs attributs sont le même niveau, un `{#id}` ne sert qu'aux liens. Un titre fait d'attributs seulement garde son texte (sans nom, son niveau disparaîtrait du chemin). La migration `core/0008_section_names_without_attributes` a corrigé les niveaux existants : un niveau à attributs rejoint son frère sans attributs s'il existe (le niveau gardé), sinon il est renommé ; sans recalcul, puisque `heading_path` ne change pas.
- **Titres qui sautent un niveau** (#305) : `NoteParser.check_level` relève, dans `ParsedNote.warnings`, un titre de niveau plus profond que le plus profond au-dessus de lui plus un, et un titre sans projet (`#`) au-dessus. L'analyse les accepte telle quelle (le chemin se fait des titres, pas de leur niveau, et un renommage repère un titre par la suite des titres au-dessus de lui, #299) et **ne réécrit jamais le texte**. `process_passages` les range dans `note.warnings`, comme les suites proposées (`note.follow_ups`) : l'enregistrement les montre en un avertissement (`warnings_message`), le compte rendu d'import les liste.
- **Titres répétés** (#315, `note_taking/qmd/regroup.py`, `views/regroup.py`) : un titre écrit plusieurs fois sous le même parent (même niveau, même texte tel qu'écrit, attributs et casse compris : ce qui fait le chemin des tâches, #240) n'est **jamais regroupé d'office**. L'enregistrement garde le texte et le signale (`repeated_message`), la page de la note propose « Regrouper les titres répétés », et la page de regroupement (`note_taking:regroup_review`) liste chaque titre répété avec une case cochée, les lignes qui bougent, les sous-titres entraînés et un aperçu de la note regroupée. Règle : les occurrences suivantes rejoignent la première ; leur texte d'avant tout sous-titre se place après le sien et **avant** ses sous-titres, leurs sous-titres de même nom fusionnent récursivement, les autres s'ajoutent à la suite ; une ligne vide sépare ce qui ne se suivait pas. Le début de la note, les lignes vides de la fin et les fins de ligne Windows sont gardés. L'arbre suit les titres du parseur (`ParsedNote.heading_lines`). **Un regroupement qui changerait l'analyse n'est pas proposé** (case désactivée, raison dite) : si ce que le parseur tire de chaque ligne (titres et tags, `todo` compris) change, par exemple un bloc `{.metadata}` qui vaudrait pour un autre texte ; ou si le texte déplacé commence en retrait derrière du texte, où il continuerait une liste (une tâche changerait de parent, donc d'identité). Choisis ensemble, les titres sont revérifiés. L'écriture (`regroup_headings`, source `regroup` du log) refuse si la note a changé depuis l'aperçu (`version`) ou si un titre choisi n'est plus à regrouper ; puis la note est recalculée, et les tâches gardent leur fiche puisque leur chemin ne change pas. Pas d'annulation : l'aperçu sert de garde-fou, le log trace l'écriture.
- **Doublons probables** (#374) : `process_passages` relève les projets et les niveaux qui existaient avant l'enregistrement ; `similar_warnings` ajoute à `note.warnings`, après ceux du parseur, un avertissement pour chaque projet ou niveau **créé** alors qu'un existant (un projet, ou un niveau frère : même projet, même parent) a la même `similar_key` : casse, accents, ponctuation, pluriel simple (`reduce_word`, la règle de la recherche) ; pas de distance d'édition, trop de faux positifs entre noms courts. Rien n'est réécrit. La page Chemins marque de même les niveaux frères proches (`TreeRow.similar`), avec un lien vers le bilan de leur réunion.
- **Cases à cocher et `todo`** (#297) : le titre `TODO` n'a plus de sens propre, c'est un niveau du chemin. Le bloc `{.metadata}` accepte `todo: true` ou `todo: false` (`Level.todo`) : même portée que les tags, le niveau le plus profond qui en parle l'emporte. Une branche `todo: true` donne le tag `TODO` à ses passages (`NoteParser.current_tags`), sans modèle de plus ; `is_todo_passage` le lit. Un bloc ne remplace plus les tags d'un niveau que s'il a une clé `tags` : une clé inconnue reprenait les tags périmés d'un bloc d'avant.
- **Conversion des anciennes sections TODO** (`convert_todo_sections`, `note_taking/qmd/todo_sections.py`, commande dans `todolist`) : retire le titre `TODO` (de `##` à `######` ; le niveau 2, un simple niveau de chemin avant #297, depuis #322 ; le niveau `#` est un projet) et passe chaque élément de sa section en case, en gardant les fins de ligne. Sans `--apply`, aperçu seulement. Retirer le titre range la liste sous le titre frère qui le précédait (`### Compte rendu` puis `### TODO` : le titre `TODO` avait remplacé son frère) : le chemin des tâches change, donc leur identité (#240). La commande garde les titres d'avant et d'après de chaque morceau de section (`Chunk`) et **range les tâches déjà créées sous leur nouveau chemin** (même fiche : avancement, échéance, parent, état), avant de recalculer les notes. Une tâche revue qui perdrait quand même sa ligne annule tout. Les cases vides hors section TODO deviennent des tâches à revoir ; une section qui n'est pas qu'une liste (paragraphe, bloc, case cochée, code) est signalée et laissée telle quelle.
- **Chemin d'une tâche** (#298) : le champ des formulaires est un texte, `SectionPathField` (`core/forms.py`), dont la valeur nettoyée est la liste des niveaux (`split_path`). Le formulaire (`SectionPathForm`, `todolist/forms.py`) crée le chemin sous le projet choisi **à l'enregistrement** (`section_for`), jamais pendant la validation : un formulaire refusé ne laisse pas de section. Changer le projet d'une tâche replace son chemin sous le nouveau projet. L'autocomplétion est une `<datalist>` native (`SectionPathInput`, `core/forms/widgets/section_path.html`), alimentée par `path_suggestions` en une requête : chaque chemin une fois, avec les projets qui le portent en libellé de l'option.
- **D'une tâche à ses voisines et à sa note** (#375) : dans le détail d'une tâche, chaque niveau du chemin mène à la liste des tâches filtrée sur lui (les notes d'un niveau s'ouvrent depuis la page Chemins), et la note d'origine s'ouvre au titre de la section (`services.origin_anchor`) : le passage qui a la ligne de la tâche, donc la bonne occurrence d'un titre répété ; à défaut (ligne cochée ou retirée dans la note), le plus profond de ses titres encore écrits. Dans le tableau des tâches, le chemin est sous le titre (`TaskRow.path`, `tree.fill_paths`, une requête pour toutes les lignes), sauf s'il est celui du parent, affiché au-dessus.
- **Liste des tâches triée et filtrée** (#294, #178 ; `todolist/task_table.py`, `todolist/tree.py`) : un seul tableau arborescent, sur `core/tables.py`. Les trois filtres sont dans le panneau de l'en-tête « Tâche » : **état** (`?state=` ; `open` par défaut, qui n'est donc pas un filtre actif, `done` = racine terminée, `all` = en cours et terminées, `dismissed` = écartées, qui ne sont pas des tâches de la liste), **titre** contenant (sans casse ni accents, `core.tables.fold`), **projets et chemins** (#302 : `PathTreeFilter`, l'arbre commun en cases ; le niveau 1 est le projet, `?project=<nom>` répété, et les niveaux sont `?path=<id>` répété, descendants compris ; tout ce qui est coché est réuni par « ou »). L'arbre ne propose que les projets et niveaux qui ont des tâches **dans l'état affiché** (`counts_for`), avec leurs compteurs ; un niveau coché sans tâche reste un filtre valide. Les filtres s'appliquent à la liste Python des tâches déjà chargées pour l'arbre (`load_tasks`, une requête) : ce qui y répond forme `matching`, et `restrict_to` garde ces tâches et leurs parents, atténués (`TaskRow.muted`). L'état choisit les groupes affichés (`task_groups(done=…)`), il ne retire aucune tâche d'un arbre. **Tri** : `?sort=due` (par défaut, comme avant : échéance, sans échéance à la fin), `title` (sans casse ni accents), `progress`, `-` pour décroissant. Il s'applique aux frères à chaque niveau et aux racines (`SORTING`, `group_key` : pour l'échéance, celle de la tâche non terminée la plus proche de l'arbre), sans jamais sortir une tâche de sous son parent ; les égalités se départagent par titre puis identifiant. Les écartées ne se trient pas. Le détail d'une tâche garde son tableau, trié par échéance, sans filtres.
- **Filtre de la liste des tâches** (#298, #302) : un niveau coché (`?path=<id>`) garde les tâches du niveau et de ses descendants (`with_descendants`). Chaque tâche reste sous ses parents pour que l'arbre garde son sens (`restrict_to`, `todolist/tree.py`) ; un parent qui ne répond pas au filtre est une ligne atténuée (`TaskRow.muted`). Pas encore de filtre sur le calendrier et la frise. La colonne « Échéance » filtre l'absence d'échéance (#384, `filter_due`) : à fixer (`none`, le critère du bloc « À traiter »), voulue (`declared`), ou une échéance (`set`).
- **Renommage d'un projet** (#170, `core.views.rename_project`) : le parcours du renommage d'un niveau, en trois temps (le nom, `core.projects.check_new_project_name` : vide, identique ou nom d'un autre projet refusé, casse seule permise ; le bilan ; l'écriture), sans case à décocher : le projet est renommé en place, puis **tous** ses titres `#` sont réécrits, sinon un titre gardé recréerait l'ancien projet à l'enregistrement suivant. `core` ne connaît pas les notes : `note_taking` déclare un `ProjectRenamer` (`renaming.project_occurrences`, `renaming.rename_project_titles`) dans son `AppConfig`, lu par `app_registry.project_renamers()`. Un titre de projet est repéré par son texte entier (`renaming.project_headings`), comme le parseur nomme le projet (attributs compris, #367 ne retire les attributs que des niveaux). Le projet est renommé avant les titres, si bien que le recalcul des notes retrouve le même projet (`project_for`, casse ignorée) ; les tâches issues des notes suivent leur chemin (`note_headings_renamed`), leur fiche et leur projet ne changent pas. Le nom ne se change plus dans le formulaire du projet (`ProjectEditForm`).
- **Titre de projet renommé dans une note** (#170, `note_taking/project_renaming.py`, `pending_renames.py`) : à l'enregistrement depuis l'éditeur, `record_project_renames` compare les titres `#` d'avant et d'après, un à un (`renamed_projects` : autant de titres, un nom changé hors casse, ni l'ancien encore écrit ni le nouveau déjà présent, pas un ancien nom changé en deux nouveaux). Écrire le nom d'un projet existant n'est pas un renommage. Un renommage est gardé en base (`PendingProjectRename`, note, ancien et nouveau nom écrits) jusqu'au choix : Ctrl+S reste dans l'éditeur (#389) et le bilan vient à « Terminer l'édition ». Deux renommages qui s'enchaînent (« Alpha » → « Gamma » → « Delta ») n'en font qu'un, un retour à l'ancien nom l'oublie. Les tâches de la note suivent aussitôt leur titre (`note_headings_renamed` : `move_tasks` pour leur chemin, et `todolist.services.follow_projects` pour leur projet et leur niveau, qui changent avec le titre `#`) ; si la note a changé ailleurs aussi (passages ajoutés ou retirés), le bilan des tâches s'en charge. Après le recalcul, `add_pending_follow_up` (appelé par la vue, pas par `process_passages` : la migration `0042_passages` recalcule les notes avec le code d'aujourd'hui, avant que la table n'existe) oublie les renommages qui ne tiennent plus et met le bilan (`note_taking:project_rename_review`) **avant** les autres suites, puisqu'il peut changer les projets des tâches. Les choix (`apply_choice`) : `everywhere` réunit le nouveau projet à l'ancien (`core.projects.merge_projects` : niveaux réunis par nom, passages, tâches et cases des recherches enregistrées), qui prend le nouveau nom, puis réécrit les titres des autres notes (`rename_project_titles`) ; `here` ne change rien ; `undo` réécrit le titre de la note à l'ancien nom et supprime le nouveau projet s'il ne sert plus (`forget_project_if_unused`).
- **Fiche d'un projet** (#205, `core.views.project_detail`, `/projects/<id>/`) : tout ce qu'on sait d'un projet. `core` ne connaît aucune app : la page est faite de leurs `project_blocks`, avec un sommaire, et de l'arbre des chemins du projet en liens (`path_tree`, compteurs de `section_counts`). Choisir un niveau (`?path=<id>`, descendants compris ; un niveau inconnu ou d'un autre projet est ignoré) restreint tous les blocs : chacun reçoit un `ProjectScope` (projet, niveau, clés des niveaux, requête). Un contexte `None` n'affiche pas le bloc. **Tâches** (`todolist/project_blocks.py`) : le tableau de la liste, par état (`?state=`), un parent d'un autre projet restant atténué ; **Frise des tâches** : les mêmes lignes (`gantt.rows_chart`). **Notes** (`note_taking/project_blocks.py`) : chaque passage avec ses premiers mots, lié à son titre dans la note (`heading_id`), par note ou par chemin (`?group=`), les récents d'abord ou l'inverse (`?order=`) ; le texte entier se lit dans la vue « Document » de la recherche, un lien y mène avec le même projet ou niveau. **Images** : celles des passages. Nombre de requêtes fixe. Le résumé de l'assistant (M18) sera un bloc de rang 10, rien n'est affiché d'ici là. La pastille d'un projet y mène avec `{% project_badge projet link=True %}` (pas dans un lien ni un label), et la page d'une note liste ses projets.
- **Arbre et renommage d'un niveau** (#299) : la page « Chemins » d'un projet (`core.views.project_paths`, `core/section_tree.py`) dresse l'arbre avec ses compteurs, descendants compris ; chaque app déclare ce qui utilise un niveau (`section_usages` de son `AppConfig`, `core/app_registry.py`), comme pour les projets, et `core` compte sans la connaître. Chaque compteur est un lien (#375, `TreeRow.usages`, `SectionUsage.url`) vers la page qui liste ce qu'il compte, filtrée sur le niveau, descendants compris : la recherche (`?subjects=`) pour les passages, la liste des tâches pour les tâches, avec `state=all` parce que les terminées sont comptées. Le renommage (`core.views.rename_section`) se fait en trois temps : le nom (`check_new_name` : vide ou identique refusé, casse seule permise), le bilan, l'écriture. Après un refus à l'écriture, la vue revient au bilan avec le nom dans l'adresse, encodé (`urlencode`, #371) : un « & » ou un « # » ne le tronque pas. `core` ne connaît pas les notes : `note_taking` déclare un `SectionRenamer` (`occurrences`, `rename`) dans son `AppConfig`. **Suppression** (`core.views.delete_section`, POST seulement) : refusée si `TreeRow.total` n'est pas nul, c'est-à-dire si le niveau ou un descendant sert à un passage ou à une tâche non écartée ; sinon `Section.delete()` emporte les descendants (cascade). Le bouton est désactivé sur un niveau utilisé, avec `aria-describedby` vers le texte de l'usage (`TreeRow.usage_id`). Une tâche écartée n'est pas comptée : son `section` passe à vide (`SET_NULL`), son chemin écrit (`note_path`) reste.
- **Réécriture des titres** (`note_taking/renaming.py`) : un titre est repéré par la suite des titres au-dessus de lui, projet compris (`headings`, `find_headings`), pas par son niveau ; ceux des blocs de code et des callouts ne comptent pas, et le nom du niveau est le texte du titre sans ses attributs (#367), comme pour le parseur ; le projet se compare sans la casse (#374). `rewrite_titles` garde dièses, espaces, attributs et fins de ligne. `rename_titles` vérifie que chaque titre choisi est encore là (sinon rien n'est écrit : la note a changé depuis le bilan), puis réécrit et recalcule chaque note, en une transaction. **Tout renommé** : la vue renomme la `Section` en place avant d'écrire les notes, donc ses descendants et les tâches saisies à la main qui la portent suivent. **Renommage partiel** : l'ancien niveau garde ses notes, le nouveau naît au recalcul ; les tâches des titres réécrits passent au niveau de leur nouveau chemin, sous-niveaux compris (`follow_sections`, #443), si elles étaient rangées là où leur ligne les mettait (`placed_by_note`, évalué avant la réécriture) : un niveau choisi à la main, et les tâches saisies à la main, restent.
- **Bilan d'un renommage de niveau** (#376) : sous chaque titre, les premiers mots de sa section, sous-titres compris (`excerpts.first_words` : première ligne de texte, sans marques du Markdown, ni métadonnées, ni ouverture de bloc), et ses tâches (`HeadingOccurrence.tasks`, les trois premières citées). Les notes ne connaissent pas les tâches : `find_occurrences` envoie `sections_reviewed` avec toutes les sections du bilan (`ReviewedSection`), et `todolist` répond par leurs titres (`section_task_titles`), en un nombre fixe de requêtes. Le bilan dit ce qui suit le nouveau chemin (le compteur de `section_tree` : sous-niveaux et tâches saisies à la main compris), et liste les niveaux de même nom ailleurs (`core.sections.homonyms`, casse et accents ignorés, sauf ceux qui portent déjà le nouveau nom et le frère réuni) : chacun a un lien vers son propre bilan, avec le même nouveau nom, dans un nouvel onglet pour ne pas perdre celui-ci. Pas de renommage groupé.
- **Réunion de deux niveaux** (#373) : un nom pris par un niveau frère (`sibling_named`, casse ignorée) n'est plus refusé : le même parcours réunit les deux. Le niveau gardé est celui qui existait (nom et casse), les titres sont réécrits à son nom par le même `SectionRenamer`. Le bilan ajoute `merge_plan` : sous-niveaux de même nom réunis (récursivement, la règle de `section_for`), sous-niveaux déplacés, et parmi eux ceux de nom seulement proche (#374), qui restent deux et sont listés pour une réunion suivante ; plus ce qui change de niveau (compteurs de `section_tree`, descendants compris). **Tout réécrit** : avant les notes, `merge_section` fait passer au niveau gardé tout ce qui mène au niveau réuni (clés étrangères et relations plusieurs-à-plusieurs lues sur le modèle, comme `forget_unused_sections` : passages, tâches, écartées comprises, recherches enregistrées), réunit ou déplace ses sous-niveaux, puis le supprime ; le recalcul retrouve le niveau gardé par `section_for`. **Réunion partielle** : comme un renommage partiel, l'ancien niveau garde les notes décochées et ses tâches saisies à la main. Deux tâches de même texte d'une même note qui se retrouveraient sous le même chemin font refuser la note (`NoteRenameError`, voir ci-dessous), et toute la réunion est annulée. Réunir avec un niveau d'un autre parent (déplacer) n'est pas prévu.
- **Les tâches suivent** : avant le recalcul d'une note, `note_taking` envoie `note_headings_renamed` (note, ancien et nouveau texte). `todolist` (`follow_renamed_headings`) compare les lignes de tâches des deux textes, passage par passage (`renamed_identities`), et range les tâches déjà créées sous leur nouveau chemin (`move_tasks`, en deux temps pour la contrainte d'unicité). Même fiche : avancement, échéance, parent, état. Un passage par section écrite : renommer un titre ne fusionne ni ne sépare plus rien (deux titres qui ne diffèrent que par la casse restent deux passages, et leurs tâches suivent). Si le renommage mettait deux tâches de même texte sous le même chemin, elles ne seraient plus qu'une : la note est refusée (`NoteRenameError`), et rien n'est écrit.
- **Index plein texte** (#198, `search_index.py`) : une table virtuelle **FTS5** de SQLite (`passage_search`, migrations `RunSQL`, recréée par `0042_passages`), sans dépendance nouvelle, `unicode61 remove_diacritics 2` (casse et accents ignorés). Une ligne par passage, de même `rowid`, avec trois colonnes : le texte (`content`, sans les blocs `{.metadata}`, déjà cherchables par tag, ni les `(image:<pk>)`, la légende restant), les titres (`heading_path`), et les deux à leur forme réduite (`words`, #372, voir « Singulier et pluriel »). C'est un index **dérivé**, comme les passages dont il vient : il suit leurs enregistrements et suppressions par les signaux `post_save` et `post_delete` de `Passage` (donc aussi quand une note est supprimée, et pour un passage créé à la main), et `reprocess_notes` le reconstruit (`rebuild_index`). La migration `0042_passages` recrée la table et recalcule elle-même les passages (voir « Les passages sont dérivés et recalculés »). `match_expression` met chaque mot, à sa forme réduite, entre guillemets (tous requis, dans `words`) : aucun opérateur de FTS5 n'est interprété, un texte quelconque n'est jamais une requête mal formée. `search_passage_ids` renvoie les clés classées par `rank` (BM25). La page de recherche applique le texte **en plus** des filtres de projet et de chemin, et classe par pertinence quand il y a du texte.
- **Syntaxe de la requête** (#199, `search_query.py`, `search.py`) : une seule zone, modèle `research-paper-relationship-graph` (`references/services/search.py`). **Opérateurs en français**, casse et accents ignorés : `projet:`, `tag:`, `chemin:` (niveaux séparés par « / », `split_path`, descendants compris, dans n'importe quel projet : `projet:` restreint ; **à toute profondeur** (#365) : un niveau convient si son chemin *finit* par les niveaux écrits, qui se suivent sans trou, donc `chemin:A/B` trouve A/B, A/B/C et C/A/B, pas A/C/B ; `chemin:réunion*` : le dernier niveau est un préfixe, un mot de son nom commence ainsi, sans casse ni accents, #368), `date:`, `sans:projet` (#385 : le texte sans projet, écrit avant le premier titre `#` ; `-sans:projet` : le texte rangé ; une autre valeur est signalée et cherchée telle quelle ; `SearchQuery.no_project` vaut vrai, faux ou rien, et se cumule aux autres filtres). Valeur à espaces entre guillemets (`projet:"Mon projet"`) ; un mot suivi de deux-points inconnu reste du texte (« Re:thinking »). Le découpage est écrit à la main, pas par `shlex` : une apostrophe (« l'été ») n'ouvre pas de guillemet. **Texte** : mots (tous requis, au singulier comme au pluriel, #372), `"phrase exacte"`, `préfixe*`, `-mot` / `-"phrase"` ; ce qui va à l'index est chaque terme entre guillemets FTS5 (`quote`), donc jamais un opérateur de FTS5, précédé de sa colonne (`fts_expression` : `words` pour un mot, le texte tel qu'écrit pour une phrase ou un préfixe), les termes joints par `AND`. Les exclusions sont cherchées à part et retirées des résultats : `-mot` marche seul. **Filtres** : `projet:` et `chemin:` répétés se cumulent (un passage n'a qu'un projet et un chemin), `tag:` répété est exigé en entier, `-projet:`, `-tag:` et `-chemin:` excluent, les noms se comparent par `core.tables.fold` (en Python : le `LOWER` de SQLite ne replie que l'ASCII), ceux des niveaux de `chemin:` à leur forme réduite (#372 : `chemin:"calcul thermique"` trouve « Calculs thermiques »). **`date:`** prend une année, un mois ou un jour, ou une plage `a..b` dont une borne peut manquer ; bornes incluses, un mois va à son dernier jour (`date:2026-10` = tout octobre), bornes inversées remises dans l'ordre, deux `date:` se recoupent. **Requête mal écrite** : jamais d'erreur ; la partie illisible (date impossible, guillemet non fermé) est cherchée telle quelle et signalée en avertissement (`SearchQuery.errors`). **Adresse** : la page est en `GET ?q=…` (aussi `projects=` et `subjects=` pour les cases, qui s'ajoutent à la requête, et `no_project=on` pour la case « Sans projet », #385, réunie aux autres cases par « ou » ; son compteur suit la requête comme ceux de l'arbre, #380, et elle s'enregistre avec une recherche, `SavedSearch.no_project`), donc une recherche se partage et survit au bouton retour ; htmx remplace les résultats et met l'adresse à jour (`hx-push-url`). `results` vaut `None` tant qu'il n'y a rien à chercher (la page montre l'aide de syntaxe, ouverte), une liste après une recherche (« Aucun résultat. » si elle est vide). Avec du texte, la plus pertinente vient en premier (BM25) ; sans texte, la plus récente.
- **Résultats groupés par note** (#201, `group_by_note` dans `search.py`) : une carte par note (titre `h2`, lien vers la note), triées selon leur passage le plus pertinent ; dans chacune, les passages trouvés (`h3` : leurs titres, « Projet › A › B », lien vers la section) avec leurs tags. **Extrait** : avec du texte à chercher, `snippet()` de FTS5 sur le texte et les titres tels qu'écrits, chaque mot cherché tel que tapé et sous ses écritures au singulier et au pluriel, les termes joints par `OR` (#372) (`search_index.snippets`, une requête par lot de 500) ; le texte est **échappé** et seuls les `<mark>` sont du HTML (FTS5 pose deux caractères de contrôle, remplacés après l'échappement). Une phrase trouvée est surlignée d'un seul tenant. Sans texte (filtres seuls, exclusion seule), le passage s'affiche rendu, comme avant. **Lien vers la section** : la page d'une note donne un `id` à chaque titre (`render_note_body(…, heading_ids=True)`, `add_heading_ids`), calculé comme les identifiants automatiques de Pandoc (`heading_slug` : minuscules, ponctuation retirée sauf `_ - .`, espaces en tirets, début jusqu'à la première lettre retiré ; `{#id}` conservé ; doublons `-1`, `-2`). **Ancre exacte** (#387) : chaque passage garde l'identifiant de son titre et de ceux de son chemin (`heading_id`, `anchor_path`), calculés à l'analyse sur la note rendue (`note_heading_ids` : chaque titre de l'analyse est retrouvé, par son texte rendu, parmi les titres du plan de la page, `note_outline`, à la suite du précédent ; un titre de citation, qui prend aussi un identifiant, est donc compté) : un titre répété mène à sa propre occurrence. `heading_anchor` (l'identifiant d'un titre d'après son texte seul, celui de sa première occurrence) ne sert plus que de repli, pour un passage enregistré sans identifiants. Le texte sans projet n'a pas de titre : son résultat mène au « Début de la note ». Le rendu par défaut (`render_note_body` sans option, passages) reste sans `id`.
- **Vue « Document » lue comme une note** (#431) : la feuille, son échelle, le plan et les sections repliables sont ceux de la page d'une note : même gabarit (`reading.html`), mêmes scripts. `document_layout` passe le document assemblé par `outline_sections` ; par date, le plan montre la date seule de chaque note, puis ses titres ; par chemin, les projets et leurs niveaux. Les identifiants des titres commencent par `doc-` (`DOCUMENT_PREFIX`) : sinon, un niveau « Results » prendrait celui de la zone que htmx remplace. **En-tête** : le bandeau collant d'une note, sur toute la largeur : titre de la page, nombre de passages, affichage, regroupement, tri (`search_options.html`, au-dessus des extraits dans l'autre vue) et bouton « Plan ». Il est hors de `#results` : une réponse htmx remplace ses options hors bande (`#results-options`). `note_reading.js` mesure sa hauteur (`--reading-top`), qui place les filtres, le plan et les ancres dessous. La colonne des filtres y est à son minimum (16 rem), et le plan n'a sa propre colonne qu'à partir de `2xl` (`beside` ; `lg` sur la page d'une note) : en dessous, il s'ouvre par-dessus la feuille. Les classes que pose `note_reading.js` sont écrites dans `reading.html` (attributs `data-*`), pas dans le script. **htmx** remplace le document entier : `note_sheet.js` (avant l'affichage) et `note_reading.js` se remettent en place sur le nouveau, ce dernier retirant les écouteurs de l'ancien (`AbortController`) ; après un retour en arrière, qui relance les scripts de la page, une seule mise en place (`window.noteReadingStart`, `window.noteSheetStart`).
- **Filtres collants** (#432, `notes_search.html`) : sur une fenêtre d'au moins `lg`, `<search>` colle en haut de `<main>` et prend au plus la hauteur visible sous l'en-tête et le titre de la page (pour que le bas du bloc soit visible sans défiler) ; au-delà, il défile dans son cadre, le bouton « Rechercher » collé en bas, et un nom trop long passe à la ligne (`wrap-anywhere`) plutôt que de le faire défiler de côté. En dessous de `lg`, les filtres sont au-dessus des résultats et ne collent pas ; à l'impression, ils sont masqués.
- **Tri des résultats** (#430, `search.py` : `result_sort`, `sort_passages`) : « Trier par », dans la barre des résultats, `?sort=relevance`, `newest` ou `oldest`. Par défaut, et pour une valeur inconnue ou impossible : la pertinence s'il y a des mots cherchés (`SearchQuery.has_words` : un mot exclu seul n'en est pas un), les notes les plus récentes d'abord sinon. Par date, chaque note garde l'ordre où elle est écrite, et les résultats élargis (#200) ne passent plus après les exacts. Avec des filtres seuls, « Pertinence » reste visible mais grisée, avec la raison en info-bulle. La vue « Document » (les deux regroupements) n'a que le sens des dates (`oldest_first`). Le formulaire garde le tri choisi, même quand il ne s'applique pas à la recherche en cours ; une recherche enregistrée ne le garde pas (`Filters`). Pas de tri par projet ni par chemin : c'est le rôle du regroupement.
- **Présentation des résultats** (#356, `search.py` : `result_options`, `document_layout` ; `search_document.py`) : deux vues, choisies dans l'adresse, `?view=extraits` (par défaut, la vue ci-dessus) ou `?view=document` ; une valeur inconnue retombe sur le défaut. Un `<nav aria-label="Présentation des résultats">` de liens (balise `result_option_url`, `search_tags.py`) change l'option en gardant le reste de l'adresse ; sans JavaScript. **Chemin ascendant** : chaque résultat de la vue extraits montre les niveaux au-dessus de sa section en fil d'Ariane (`<nav aria-label="Chemin du résultat">`, `Hit.crumbs`), chacun lié à son ancre dans la note ; le dernier niveau est le titre `h3` du résultat. Le texte d'un titre est affiché sans ses attributs (`{#id}`). Le fil est absent d'un résultat dont le chemin est le projet seul. **Document** : `assemble` (sans accès à la base) remet les passages bout à bout en un seul Markdown, que `render_passage` rend comme une note ; les numéros des tableaux et figures se calculent donc sur le texte assemblé, comme prévu à #278. Titres re-créés d'après les **niveaux en base** (#369, `levels_of`) : le projet (« Sans projet » pour le texte avant le premier `#`, `NO_PROJECT`), puis `Passage.section` et ses ancêtres, chacun sous son nom en base (`Level`, son identité et son nom) ; `##` à `######`, le dernier niveau est gardé au-delà ; le `h1` reste celui de la page, `h2` = un groupe. Un titre déjà ouvert n'est pas répété, un retour à un niveau plus haut le réécrit ; les niveaux se comparent par identité, pas par texte. Auparavant, les titres venaient de `heading_path`, tels qu'écrits : chaque écriture d'un même niveau (casse, blancs) ouvrait un groupe, et le tri sans casse ni accents donnait la même clé à des groupes distincts (« Chantier Nord » et « Chantier nord », deux projets ; « Réunion » et « Reunion », deux niveaux), qui s'entrelaçaient alors selon la date, un projet étant rouvert plus bas. `?group=date` (par défaut) : un `h2` par note (lien vers la note), les plus récentes d'abord, dessous le projet (`h3`) et ses niveaux, les passages d'une note dans l'ordre où ils sont écrits (`position`, #387 : avant, une note part réunissait les lignes d'un même chemin écrites à deux endroits) ; deux passages qui se suivent sous le même niveau écrit autrement (« Réunion de Chantier », puis « Réunion de chantier ») restent sous un seul titre, ce que la comparaison des titres écrits ne faisait pas. `?group=path` : l'arbre Projet (`h2`) › niveaux, trié sans casse ni accents puis, à nom égal, par identité (projet, puis section : `tree_order`), pour que deux groupes distincts ne s'entrelacent jamais et que le même projet ne soit jamais rouvert ; parents avant enfants, et sous chaque niveau les passages de toutes les notes, le plus récent d'abord, chacun précédé de sa date en lien vers sa section, à sa propre occurrence dans sa note. Les mots trouvés ne sont pas surlignés dans le document. Le formulaire de la colonne de gauche (htmx) renvoie `view` et `group` (champs cachés) : modifier la recherche garde la vue.
- **Fautes de frappe** (#200, `search.py` : `expand_query`, `search_index.py` : `similar_terms`) : un mot libre **sans résultat ou rare** (dans moins de `RARE` = 2 passages) est élargi aux mots proches de l'index. Le vocabulaire est la table `passage_vocab` (FTS5vocab sur `passage_search`, migrations `RunSQL`, rien à remplir : c'est une vue de l'index) ; depuis #372, une vue par colonne dont on ne lit que `words` : le seuil `RARE` et les mots proches portent sur les formes réduites, le singulier et le pluriel comptés ensemble, et « thermiques » n'est plus un mot proche de « thermique ». La proximité est une distance de Damerau-Levenshtein calculée en Python (`edit_distance` : l'échange de deux lettres voisines compte pour 1), sur des mots déjà sans casse ni accents, comme l'index : **une faute pour 4 à 6 lettres, deux au-delà, aucune sous 4 lettres** ; au plus `MAX_ALTERNATIVES` = 3 mots proches par mot, le plus proche d'abord puis le plus fréquent. **Jamais élargis** : une phrase entre guillemets, un préfixe `mot*`, un terme exclu, les valeurs d'opérateurs (`projet:`, `tag:`…), un mot avec chiffre ou ponctuation. La requête élargie remplace le mot par `("écrit" OR "proche")` et joint les termes par `AND` explicite (FTS5 refuse un groupe entre parenthèses collé à un autre terme). **Les résultats exacts passent avant les élargis**, même moins pertinents ; on n'élargit que si l'élargissement ajoute au moins un résultat. Les mots utilisés sont dans `SearchQuery.expansions` (écrit, trouvé), montrés par `search_expansion.html` (« thermiqe → thermique ») avec un lien qui annule : `?exact=1` coupe l'élargissement (`expand=False`) ; depuis #372, les mots restent cherchés à leur forme réduite, d'où le libellé « Chercher sans corriger les fautes » plutôt que « Chercher exactement ce qui est écrit ». Le mot trouvé est celui de l'index, donc sans accents et à sa forme réduite.
- **Singulier et pluriel** (#372, `word_forms.py`) : le singulier et le pluriel sont le même mot **dans l'index**, et non par l'élargissement aux fautes, qui ne joue que pour un mot rare : « thermique », présent dans deux passages, n'y trouvait pas « Calculs thermiques », que « thermiques », rare, trouvait par élargissement. Chaque mot a une **forme réduite**, sans casse ni accents (`fold`), par des règles écrites à la main, sans dépendance ni racinisation complète (type Snowball, qui confond trop de mots) : `-eaux` perd son x (« tableaux » → « tableau »), `-aux` devient `-al` (« journaux » → « journal »), sinon un `s` ou un `x` final est retiré (« thermiques », « bijoux »). **Un mot de moins de 5 lettres** (`MIN_LENGTH`) **ou qui contient un chiffre reste tel quel** : « mais » ne devient pas « mai », ni « mois » « moi », ni « fois » « foi ». Cas limites assumés : « bus », « os » et « gaz » restent tels quels, mais aussi « mots », « noms », « jeux » ou « lois », qui ne retrouvent donc pas leur singulier ; un pluriel en `-aux` d'un mot en `-ail` ou en `-au` ne retrouve pas son singulier (« travaux » et « travail », « noyaux » et « noyau ») ; un mot qui finit par s ou x au singulier perd aussi sa dernière lettre et peut en rejoindre un autre (« Paris » et « pari », « index » et « Inde »). La forme réduite s'applique au texte indexé et aux titres (colonne `words`), aux mots de la requête, exclusions comprises, et aux noms de niveaux de `chemin:`, dans la même comparaison que `fold`. La **phrase exacte** et le **préfixe** restent cherchés dans le texte tel qu'écrit (`content`, `headings`) : `"calculs thermiques"` ne trouve pas « calcul thermique », et `therm*` marche comme avant. **Choix technique** : FTS5 n'a pas de racinisation française, et un tokenizer personnalisé ne s'écrit pas en Python (le module `sqlite3` ne permet pas d'en enregistrer : il faudrait une extension en C ou une dépendance comme `apsw`) ; la forme réduite est donc une **colonne calculée en Python** (`indexed_words`), à côté du texte tel qu'écrit. Elle ne suffit pas au **surlignage** : `snippet()` montre le texte de la colonne où il trouve les termes, et celui de `words` est réduit (« calcul thermique » pour « Calculs thermiques »). Les extraits cherchent donc dans le texte tel qu'écrit, chaque mot tel que tapé et sous les écritures qui ont sa forme réduite (`written_forms` : « calcul » donne `("calcul" OR "calculs" OR "calculx")`, les mots élargis de même), ce qui marque le mot tel qu'il est écrit dans la note (`fts_expression(…, written=True)`). Le mot tel que tapé est toujours parmi les options : FTS5 le replie comme le texte, alors que la forme réduite passe par `fold`, qui change « m² » en « m2 », « CO₂ » en « co2 » et « ß » en « ss », écritures que le texte n'a pas ; et un mot de plusieurs morceaux dont les écritures dépassent `MAX_COMBINATIONS` (64, une adresse ou un nom de fichier) n'a que sa forme réduite, rarement écrite telle quelle (« https » y devient « http »). Les termes des extraits sont joints par `OR` : les passages montrés ont déjà tous les termes (colonne `words`), et un terme introuvable tel qu'écrit (une adresse recopiée au pluriel) ne retire pas l'extrait des autres ; le passage n'est montré rendu, sans surlignage, que si aucun terme n'y est trouvé tel qu'écrit. Ces écritures suffiraient à chercher sans colonne de plus ; l'index garde la règle à un seul endroit, et le vocabulaire des formes réduites compte le singulier et le pluriel ensemble pour l'élargissement (#200). **Index existant** : une table FTS5 ne prend pas de colonne de plus ; la migration `0040_notepart_search_words` recrée la table, reprend ses lignes telles quelles et calcule leur colonne `words` (copie figée des règles), sans commande à relancer ; `reprocess_notes` reconstruit l'index comme avant. Changer les règles demande de reconstruire l'index : `reprocess_notes`, ou une migration comme `0040`.
- **Niveaux de `chemin:`** (#368, `search_paths.py`, gabarit `search_paths.html`) : au-dessus des résultats, chaque `chemin:` (ou `-chemin:`) de la requête dit les niveaux qu'il retient (« chemin:"réunion de chantier" → 2 niveaux : Chantier Nord › Réunion de chantier, Chantier Sud › Lot 2 › Réunion de chantier »), en `role="status"`, pour voir ce que la casse, les accents et le pluriel ont replié. **Aucun niveau** : un avertissement (« Aucun niveau ne s'appelle « reunion ». ») et des requêtes à essayer, en liens qui gardent le reste de l'adresse (`result_option_url`). Elles ne sont **que proposées**, jamais appliquées : un chemin est un filtre, et l'élargir sans le dire mélangerait des branches (contrairement aux fautes du texte, #200). Dans l'ordre : les **guillemets oubliés** (`chemin:réunion de chantier`, où « de chantier » est lu comme du texte : si les mots qui suivent complètent un nom de niveau, la même valeur entre guillemets, seule proposée), le **projet écrit en premier niveau** (`chemin:"Chantier Nord/Réunion"` → `projet:"Chantier Nord" chemin:Réunion`, si ce chemin existe dans ce projet ; `chemin:"Chantier Nord"` seul → `projet:"Chantier Nord"` ; jamais pour une exclusion, `-projet:A -chemin:B` n'excluant pas « A › B »), puis les **noms proches** : chaque niveau écrit est une partie du nom (au moins 3 lettres) ou à peu de fautes de lui (`tolerated_typos`, la règle de #200, déplacée dans `search_index.py`) ; le nom exact, puis la partie, puis le moins de fautes d'abord, un même chemin proposé une fois quel que soit son projet, au plus 5 propositions. La requête proposée est réécrite jeton par jeton (`read_tokens`) : le reste est gardé tel qu'écrit, un « / » d'un nom est doublé, un nom à guillemet n'est pas proposé.
- **Recherches enregistrées** (#203, `saved_searches.py`, `views/saved_searches.py`, `SavedSearch`) : une recherche gardée sous un nom : **le texte de la zone `q`**, tel qu'écrit, **et les cases cochées de l'arbre** (#380, `SavedSearch.projects` et `SavedSearch.sections`, plusieurs-à-plusieurs : un projet ou un niveau supprimé quitte la recherche, sans laisser d'adresse invalide). Jusqu'à #380, seul le texte était gardé ; depuis que l'arbre est le moyen principal de filtrer par chemin (#357, #360), une recherche filtrée par l'arbre seul affichait « Lancer une recherche pour pouvoir l'enregistrer. » avec ses résultats à l'écran. `Filters` (`saved_searches.py`) est ce qui fait une recherche dans l'adresse (`?q=…&projects=…&subjects=…`, `Filters.read`, `Filters.url`) ; une clé qui n'est pas un nombre, ou inconnue, est ignorée. Il faut au moins du texte ou une case. Le nom proposé est le texte, ou à défaut les projets puis les niveaux cochés (« Chantier Nord › Réunion »), et la recherche en cours (`aria-current`) est celle qui a le même texte et les mêmes cases. Le nom est unique sans tenir compte de la casse ni des accents : contrainte `unique` en base, et comparaison par `core.tables.fold` en Python avant l'écriture (le `LOWER` de SQLite ne replie que l'ASCII), pour répondre « Une recherche nommée … existe déjà » au lieu d'une erreur 500 ; une recherche peut changer la casse de son propre nom. Erreurs métier en `SavedSearchError` (nom vide ou de plus de 100 caractères, nom pris, requête vide), affichées en toast. **Trois vues POST** (`/notes/search/saved/`, `…/<id>/rename/`, `…/<id>/delete/`), puis retour à la page de recherche : la recherche en cours voyage dans l'adresse (`?q=…&projects=…&subjects=…`, encodée par `urlencode`, donc sans en-tête injectable), si bien qu'on la retrouve telle quelle même après une erreur. La suppression passe par la popover native de `confirm_button` (#292), sans nom d'objet dans la question. **La page de recherche n'a qu'une ligne à ajouter** : la balise d'inclusion `{% saved_searches form.q.value %}` (`templatetags/search_tags.py`, gabarit `saved_searches.html`) charge elle-même la liste et le formulaire « Enregistrer cette recherche » (nom proposé : la requête) ; la vue ne lui passe rien. La recherche en cours est marquée `aria-current`. Comme les résultats se mettent à jour sans recharger la page (htmx), `saved_searches.js` fait suivre au formulaire d'enregistrement la zone de recherche et les cases cochées (des champs cachés `projects` et `subjects`) ; sans script, il envoie la recherche de l'adresse. Le formulaire est toujours rendu, **caché** (`hidden`) quand il n'y a rien à enregistrer, et le script le montre dès qu'on tape ou coche, à la place du message.
- **Filtres de la page de recherche** (#302, `core/path_tree.py`, `{% path_tree %}`) : les chemins s'affichent dans l'**arbre des chemins** commun (voir « Composants d'interface »), en cases `name="subjects"`, dans un seul `fieldset` « Projets et chemins » ; le niveau 1 de l'arbre est le projet, en case `name="projects"` (#360, `project_param`). Plus de bloc `<details>` autour d'eux, ni de rechargement des chemins quand on coche un projet : l'arbre montre les projets utilisés ou choisis (compteur `search.project_counts`, même sans niveau) avec leurs niveaux, et seuls les niveaux utilisés par des passages, avec leurs parents implicites, sont proposés (`only_counted`). Compteurs par niveau (`search.section_counts`, descendants compris par le composant), en passages (`count_noun="passage"`, #362). Choisir un niveau cherche aussi ses descendants (`with_descendants`) ; les niveaux choisis sont cochés et leurs parents ouverts, sans JavaScript. **L'arbre suit la requête** (#380) : avec une requête, ses compteurs sont ceux du **résultat** (facettes, `search.facet_counts`, sur les passages déjà trouvés, sans requête de plus), calculés **sans les cases de l'arbre** (sinon cocher un niveau mettrait tous les autres à 0 ; une seconde recherche, sans `projects` ni `subjects`, quand des cases sont cochées). Les niveaux gardés restent ceux de toute la base (`path_tree(…, used=, project_used=)` : ce qui décide des nœuds gardés par `only_counted`, quand le compteur affiché en diffère), et un nœud à 0 reste affiché, atténué (`{% path_tree … faceted=True %}` : « (0) » et `data-zero` sur le compteur, le libellé en `text-slate-500` par `[&:has(>[data-zero])]`). Sans requête, les compteurs de toute la base, comme avant. Les niveaux **retenus par `chemin:`** (`PathReport.section_ids`, sans descendants ni `-chemin:`) sont marqués (`path_tree(…, marked=)`, pastille « chemin: ») et leurs parents ouverts, **sans être cochés** : ce n'est pas le même filtre (par nom, à toute profondeur et dans tous les projets, contre un niveau précis). **Mise à jour htmx** : la réponse ne remplace que les résultats ; le compteur et la marque de chaque nœud sont dans `#<clé>-facet` (`core/components/path_tree_facet.html`), renvoyés hors bande (`hx-swap-oob`) dans la réponse htmx seulement. L'arbre lui-même n'est pas renvoyé : remplacer ses cases ferait perdre le focus de celle qu'on vient de cocher et refermerait les niveaux ouverts. `search_tree.js` ouvre ensuite les parents des niveaux marqués (`htmx:afterSettle`), sans jamais refermer un niveau. Les cases s'ajoutent à la requête (`?q=…&projects=…&subjects=…`) ; projets et niveaux cochés sont réunis par « ou » (un projet et le chemin d'un autre projet donnent les deux), comme dans la liste des tâches, et le texte et la syntaxe restreignent ce résultat ; htmx recharge les résultats à chaque changement.
- `reprocess_notes` recalcule les passages, puis supprime les tags que plus rien n'utilise (`core/tags.py`) : un enregistrement de note ne supprime jamais de tag, pour ne pas faire disparaître un tag créé à la main. Les tâches déjà créées gardent leur section : une tâche générée prend celle de son passage à sa création.

### Images (#25, #26)

- Modèle dans l'app `images` ; les **pages restent dans la prise de notes**.
- Une image est référencée dans une note par son **nom de fichier**, quel que soit le dossier écrit. À l'analyse, la référence devient `image:<pk>` dans le contenu du passage.
- Le nom se tire du chemin par une seule fonction, `rendering.images.image_name`, commune à l'analyse, au rendu et à l'export (#220) : dossier ignoré, `\` traité comme `/`, et `None` pour une URL externe (`http(s)://`, `data:`, chemin absolu). Une image sur un autre serveur n'est pas chargée : le rendu en fait un lien vers son adresse (`remote_images_as_links`).
- Le **format** (vectoriel ou matriciel) se déduit de l'extension du fichier (`is_vector`), l'**origine** de la présence d'une source (`is_editable`) : ce sont deux notions indépendantes, sans champ dédié.
- Le lien vers les images est porté par le **passage**, là où l'image est utilisée (texte sans projet compris, #385) : on sait dans quel projet, sujet et avec quels tags elle apparaît. `Note.images` en est déduit.

### Liens entre notes (#206, #207)

- **Syntaxe** : un lien vers une note est un lien Markdown ordinaire vers sa date, `[texte](AAAA-MM-JJ)` ou `[texte](AAAA-MM-JJ#ancre)` : un lien relatif valide pour Pandoc, sans syntaxe propre à l'application. Quarto ne reconnaît une page du projet qu'à son fichier : **l'export ajoute `.qmd`** (`qmd/links.to_quarto`, dans `note_to_qmd`) et Quarto en fait un lien vers la page `.html` voisine ; **l'import et le remplacement du fichier source le retirent** (`from_quarto`, dans `services`), si bien qu'un aller-retour rend le corps tel quel. La réécriture ne touche ni le code (blocs et code en ligne) ni les images. La forme `AAAA-MM-JJ.qmd` est lue partout aussi (analyse, rendu, migration `0044`). Rien d'autre ne suit la date dans le lien (`2026-03-12-bis`, `2026-03-12.pdf` ne sont pas des notes).
- **Rendu** : `resolve_note_links` (`rendering/note_links.py`) retouche le HTML filtré, après tout le reste (`render_note_body`, `render_passage`) : une seule requête pour les dates citées. Le lien mène à la page de la note, à l'ancre écrite (les identifiants des titres suivent ceux de Pandoc, #201). Une note absente est **signalée, pas refusée** : le lien garde son texte, marqué comme cassé (souligné en pointillés, rouge, avec un titre explicatif) et mène à la création de la note à cette date ; l'enregistrement le dit dans un toast à part (`Note.missing_links`, `save_warnings`), pas dans `note.warnings` dont le message compte des titres. L'ancre n'est pas vérifiée.
- **Lien sans texte** (#467) : `fill_empty_links` (`rendering/empty_links.py`) lui donne son adresse pour texte, ou « Note du … », ou le titre visé par une ancre. Il passe après les identifiants des titres, pour que ce texte n'y entre pas (l'ancre reste celle de Pandoc, donc de l'export), et avant `resolve_note_links`, qui remplace l'adresse écrite ; le tout dans `finish_links` (`rendering/notes.py`).
- **Nouvel onglet** (#438) : `open_links_in_new_tab` (`rendering/new_tab.py`), dernière étape du rendu, donne `target="_blank"` et `rel="noopener noreferrer"` à tout lien qui quitte la page (site, `mailto:`, image distante, note, existante ou absente) ; une ancre ou un renvoi `@fig-…` y reste. Le filtrage retire toujours le `target` écrit dans une note. La marque ajoutée au lien est une flèche décorative, collée au dernier mot (espace fine insécable), absente à l'impression et d'un lien réduit à une image, puis un texte masqué « (nouvel onglet) ». Posée après les identifiants des titres, elle n'entre pas dans une ancre ; le plan et `heading_texts` la retirent (`without_new_tab_marks`).
- **Lien vers un fichier** (#496) : `[texte](C:\…)`, `C:/…`, `\\serveur\…`, `//serveur/…` ou `file:…` n'est pas un lien, qu'un navigateur refuserait de suivre, mais le texte suivi d'un bouton « Copier le chemin » (`rendering/file_paths.py`). `FilePathLinkExtension` lit le lien avant les échappements du Markdown (priorité 185, après le code), sans quoi `\\serveur` perdrait une barre ; il en sort un repère (`<span class="file-path-copy-marker" title="…">`) que le filtrage garde, et que `file_path_buttons`, après lui, remplace par le bouton : le chemin Windows à copier (`copied_path` : `file:` retiré, `%20` décodés, `/` en `\`) dans `data-copy-path` et l'info-bulle. Le bouton n'a qu'une icône et un `aria-label` : il n'entre ni dans le texte ni dans l'identifiant d'un titre. Un chemin Linux (`/home/…`) ne se distingue pas d'une adresse du site et reste un lien ; `//serveur/…` est un chemin réseau, pas une adresse sans schéma. `note_taking/static/note_taking/file_paths.js` (gabarit de base des notes, écouté sur le document pour les résultats chargés par htmx) copie par `navigator.clipboard.writeText` en contexte sécurisé, sinon par une zone de texte sélectionnée et `execCommand("copy")`, et le confirme d'un toast ; à défaut, le chemin s'affiche à copier à la main. À l'impression, `style.css` remplace l'icône par le chemin entre parenthèses.
- **Liens portés par le passage** (`PassageNoteLink`), comme les images : recalculés avec les passages, à chaque enregistrement et par `reprocess_notes`. La note citée est désignée **par sa date, pas par une clé** : un lien vers une note qui n'existe pas encore est gardé, et la note, une fois créée, voit qui la cite. Un lien écrit dans du code (bloc ou en ligne) n'en est pas un ; une date impossible est ignorée.
- **Citée par** : la page d'une note liste les passages des autres notes qui la citent (`note_citations.citations`), des notes les plus récentes aux plus anciennes, un passage une fois même s'il la cite plusieurs fois : la note qui cite, le projet en pastille et le chemin sous le projet, la ligne du lien en texte (160 caractères au plus), et un lien vers le titre du passage (`heading_id`).
- **Migration** : `0044_passagenotelink` crée la table puis calcule les liens des passages existants avec une copie figée de `qmd/links.py` : `reprocess_notes` n'est pas nécessaire.

### Suppression protégée

Un objet utilisé ne peut pas être supprimé (`on_delete=PROTECT`) :

- un **projet** utilisé par un passage ou une tâche ;
- une **section** utilisée par un passage (celle d'une tâche passe à vide à la suppression, elle est facultative) ;
- une **image** utilisée par un passage (via `PassageImageLink`).

Django refuse la suppression (`ProtectedError`) et l'admin liste les éléments concernés.

Dans l'interface, une image se supprime depuis sa page de détail (#85) : le bouton est désactivé, avec la raison, tant que l'image est utilisée. Le service `images.services.delete_image` s'appuie sur la même protection : il traduit la `ProtectedError` en erreur métier (`ImageInUseError`), sans connaître les apps qui utilisent les images, et n'efface les fichiers qu'une fois la suppression validée en base.

### HTML des notes filtré (#241)

Le HTML qu'écrit l'utilisateur, directement ou par le Markdown, passe par une liste blanche (`nh3`, dans `render_plain_markdown`) : balises d'un document (texte, titres, listes, tableaux, images, liens, code, `details`…), attributs `class`, `id`, `title`, `href`, `src`, `alt`, `width`, `height`, `style` limité à `text-align` sur les cellules, et URL en `http`, `https`, `mailto` ou relatives. Un script, un gestionnaire `on…`, un cadre ou un lien `javascript:` est retiré : il s'exécuterait dans la page et pourrait envoyer les notes ailleurs. Le HTML des blocs Quarto (callouts, grilles, colonnes, icônes) est construit autour, à partir de valeurs échappées ou contrôlées, et n'est pas filtré.

**Aucune image d'un autre serveur** (#220, #458) : le navigateur la chargerait en ouvrant la note. `![…](https://…)` devient un lien dès le Markdown ; toute autre écriture (référence, titre entre apostrophes, adresse sans schéma, `<img>` en HTML) l'est à la fin du filtrage (`remote_images_as_text`), où l'adresse est jugée comme le navigateur la lit (`is_remote`). Dans un lien, il ne reste que le texte de l'image. En seconde barrière, `SECURE_CSP` (en-tête `Content-Security-Policy: img-src 'self' data:`) fait refuser par le navigateur une image qui passerait quand même ; les autres ressources n'y sont pas limitées.

Après le filtrage, chaque image du contenu reçoit `loading="lazy"` et `decoding="async"` (#225) : une note longue ne charge que les images proches de l'écran. La liste des images fait de même.

### Rendu fidèle à Quarto (M11)

Le rendu suit le Markdown de Pandoc, celui de Quarto, et non les règles propres à Python-Markdown. Un écart se corrige par une extension Markdown du paquet `rendering` (`lists.py`, `tables.py`, `inline.py`, réunies dans `markdown.py`), testée sur les résultats de Pandoc. Les écarts voulus et les syntaxes non prises en charge sont dans [`ecarts-pandoc.md`](ecarts-pandoc.md) : toute issue qui s'écarte de Pandoc y ajoute sa ligne.

- Sous-listes (#229) : un élément est imbriqué si son marqueur commence au moins à la colonne du texte de l'élément parent (2 espaces après `- `, 3 après `1. `). `PandocListsExtension` réindente les listes par multiples de 4, seul pas que comprend Python-Markdown ; un changement de type de liste commence une autre liste (`sane_lists`). Python-Markdown lit tout un bloc au niveau de sa première ligne : `DedentedItemsProcessor` ramène à leur niveau les éléments qui sortent de la sous-liste par laquelle le bloc commence (#482). Python-Markdown ne reconnaît un bloc de code délimité qu'en début de ligne : celui d'un élément, indenté, est mis de côté par le prétraitement, sans l'indentation de sa clôture, avec le préprocesseur de `fenced_code` (#489). Le texte d'une citation, que Python-Markdown ne prétraite pas, est prétraité à part, sans ses `>` : ses listes et ses blocs de code sont ceux du reste de la note (#490). Un titre collé à la suite d'un élément en sort, comme pour l'analyse (#491). La règle est dans `qmd/lists.py` : les sous-tâches issues des notes (#238) la suivent aussi.
- Marqueurs de liste de Pandoc (#325) : lettres (`a.`, `A)`, `(a)`), chiffres romains (`i.`, `iv)`, `(IX)`), numérotation automatique (`#.`) et exemples numérotés (`(@)`, numérotés dans tout le document) sont ceux de l'extension `fancy_lists`, active par défaut dans le Markdown de Quarto (vérifié avec Pandoc 3.10 et `quarto render` 1.10.19) ; ce n'est pas du Markdown standard (CommonMark, GitHub), où ils restent du texte. La grammaire est dans `qmd/lists.py` (`parse_marker`, `Marker`) et sert au rendu, aux sous-tâches des notes (#238) et au convertisseur. Règles relevées sur Pandoc : une lettre est **une seule** lettre (`c.` est la lettre 3, pas le chiffre romain 100) ; un chiffre romain est `i`/`I` seul ou plusieurs lettres valides (`ii.`, `iv.`) ; une majuscule seule suivie d'un point (`A.`, `I.`) demande **deux espaces**, sinon c'est une initiale ; **le contexte décide** des lettres ambiguës une fois la liste commencée (`i.` reste la lettre i dans `a.`, `b.`, `i.` ; `v.`, `x.`, `c.` restent des chiffres romains dans `iv.`, `v.`) ; un autre type, une autre casse ou un autre séparateur (`a.` puis `b)`) ouvre une autre liste ; la liste commence au rang de son premier marqueur (`c.` → `start="3"`) ; une liste ne peut pas interrompre un paragraphe (`a.` collé à du texte reste du texte, `#.` n'est pas un titre). `PandocListsPreprocessor` réécrit ces marqueurs en `N.`, note le type de la liste en tête du premier élément par une balise de l'usage privé que `ListTypeTreeprocessor` convertit en attribut `type` du `<ol>`, comme Pandoc, et en classe (`list-lower-alpha`, `list-upper-alpha`, `list-lower-roman`, `list-upper-roman`), que le filtre nh3 conserve et que `style.css` affiche : un sélecteur sur `type` ne distinguerait pas `a` de `A` (en HTML la valeur de `type` se compare sans tenir compte de la casse, et Chrome ignore le drapeau `s` qui y remédierait) ; deux listes numérotées qui se suivent sont séparées par un commentaire, retiré au filtrage, puisque Python-Markdown les fusionnerait. Les éléments `(@)` ne sont pas des références croisées : `(@étiquette)` n'est pas résolu dans le texte. La coloration de l'éditeur ne connaît pas ces marqueurs (voir l'éditeur).
- Cases à cocher (#231) : un élément qui commence par `[ ]`, `[x]` ou `[X]` suivi d'un blanc devient une case dans un `<label>`, comme dans Pandoc ; une liste à puces faite uniquement de cases reçoit la classe `task-list`, sans puces. `TaskListExtension` pose le `<label>` ; la case (`<input type="checkbox" disabled>`) n'est ajoutée qu'après le filtrage nh3, dont la liste blanche n'accepte aucun champ de formulaire. Les cases sont désactivées : la page affiche la note sans la modifier. Une tâche issue d'une ligne à case garde son propre état : une case cochée ne la termine pas (#222, voir #237).
- Légendes de tableau (#230) : un paragraphe qui commence par `:` ou `Table:`, juste avant ou juste après un tableau, avec ou sans ligne vide, devient son `<caption>` ; celle d'avant l'emporte. Des attributs `{#tbl-x .classe}` en fin de légende vont au tableau. `TableCaptionExtension` sépare d'abord une légende collée au tableau, puis déplace le paragraphe dans le tableau. La numérotation croisée de Quarto (« Table 1: » pour un tableau `#tbl-…`) n'est pas reprise : un passage est rendu seul, sans le reste de la note.
- Exposants, indices et barré (#271) : `^…^` en `<sup>`, `~…~` en `<sub>`, sans espace dans le contenu sauf échappée (`\ `, espace insécable) ; `~~…~~` en `<del>`, reconnu avant l'indice, qui utilise lui aussi le tilde. `\^` et `\~` restent du texte. Les motifs inline de `SuperscriptSubscriptExtension` passent avant l'emphase, qui reste rendue à l'intérieur. Une formule LaTeX (#99) passe avant : `$x^2^$` ne produit pas d'exposant HTML.
- Souligné (#434) : `[texte]{.underline}` devient `<span class="underline">` (la classe de Tailwind). De l'extension `bracketed_spans` de Pandoc, seule cette classe, seule, est reconnue. `UnderlineExtension` passe après le code, les liens et les images (une légende ou un lien peut contenir du souligné) et avant un lien par référence, comme Pandoc ; l'identifiant d'un titre est donc celui de son texte.
- Formules LaTeX (#99) : `$…$` en ligne (pas d'espace après le premier `$` ni avant le second, pas de chiffre juste après) et `$$…$$` en bloc, éventuellement sur plusieurs lignes. `MathExtension` garde la formule telle qu'écrite, sous la forme de Pandoc avec MathJax, celle de Quarto : `<span class="math inline">\(…\)</span>` ou `math display` et `\[…\]`. Ses motifs passent avant tous les autres sauf le code : ni l'emphase, ni les exposants, ni les caractères échappés ne touchent une formule ; `\$` reste un dollar. KaTeX, embarqué dans `static/vendor/katex/` (polices `woff2` seulement), affiche la formule dans le navigateur : `note_taking/static/note_taking/math.js`, chargé par le gabarit de base des notes, rend les formules à l'ouverture de la page et après chaque échange htmx (`htmx:load`). Sans JavaScript, la formule reste lisible telle qu'écrite. KaTeX plutôt que MathML : rendu identique d'un navigateur à l'autre, et la syntaxe LaTeX des notes s'affiche sans conversion côté serveur.
- Figures implicites (#422) : une image seule dans son paragraphe, avec un texte, devient une `<figure>` dont ce texte est la légende, Markdown compris (`ImplicitFiguresExtension`, `rendering/figures.py`, l'extension `implicit_figures` de Pandoc) ; sans texte, ou au milieu d'une ligne, elle reste une image. Un identifiant `{#fig-…}` passe à la figure. L'`alt` est `fig-alt` s'il est donné, sinon le texte de la légende sans sa mise en forme. Les motifs d'image de Python-Markdown sont remplacés par d'autres qui gardent le texte entre crochets dans l'élément `img` le temps de l'analyse en ligne. La légende d'une image peut contenir des crochets appariés, un lien par exemple : le motif `CAPTION` (`rendering/images.py`) est commun à l'analyse, au rendu et à l'export (#453) ; l'image entière est reconnue avant de regarder si son adresse est distante.
- Numéros des tableaux et figures (#278) : `number_floats` (`rendering/floats.py`) numérote le HTML rendu, comme Quarto 1.10.19 (qui écrit « Table 1: » et « Figure 1: », même avec `lang: fr`). Un tableau à `{#tbl-…}` et à légende, une figure en colonnes ou une image seule à `{#fig-…}` reçoivent « Table N » ou « Figure N », chaque sorte comptée à part, dans l'ordre du texte. Sans légende, la légende se réduit à « Figure N », comme dans Quarto. Les images d'une figure en colonnes ont leur légende, sans numéro (Quarto les numérote 1a, 1b : écart connu). Les références `@tbl-x` et `@fig-x` du texte deviennent des liens `<a class="quarto-xref">` vers le numéro, sauf dans le code et dans un lien ; une référence sans cible s'écrit `?@x` en gras, comme dans Quarto. **Les numéros repartent de 1 à chaque rendu et dépendent du texte rendu** : la page d'une note numérote sur la note entière (`render_note_body`), un passage seul sur lui-même (`render_passage`), et un passage qui cite un tableau d'un autre n'a pas sa cible. Le numéro d'un même tableau peut donc différer entre la note et son extrait, écart assumé avec Quarto (décision du 2026-10-27). Un futur résultat de recherche ou une fiche projet numéroteront de même leur texte assemblé.

### Éditeur des notes (#89)

L'éditeur est **CodeMirror 6**, embarqué dans `static/vendor/codemirror/` (aucun CDN), et non un `<textarea>` enrichi : les suggestions dans le texte (projets, chemins, images, plus tard les notes), les soulignements de l'assistant (M18) et l'historique d'annulation après une insertion ne se font pas proprement sur un `<textarea>`.

- **Le `<textarea>` reste** : `editor.js` (module ES, `note_taking/templates/note_taking/note/form.html`) le cache et le remplace par CodeMirror, qui le tient à jour à chaque frappe ; c'est lui que le formulaire envoie. Si le module ne se charge pas, on écrit dans le `<textarea>`.
- **Garde-fous** (#228) dans `note_form.js`, un script classique indépendant de CodeMirror : Ctrl+S envoie le formulaire, et quitter la page avec un texte ou une date modifiés déclenche l'avertissement du navigateur (`beforeunload`), levé à l'envoi. Une page rendue avec des erreurs porte `data-unsaved` : ce qu'elle affiche n'est pas enregistré.
- **Capture rapide** (#386) : Ctrl+Maj+K (⌘⇧K), ou le bouton à droite de l'en-tête, ouvre sur toutes les pages un `<dialog>` natif qui ajoute une ligne à la note du jour sans quitter la page (`quick_capture.js`, `views/capture.py`). Le gabarit (`note_taking/quick_capture.html`) est déclaré par l'`AppConfig` (`header_templates`, lu par `app_registry.header_templates()` et le processeur de contexte) : `core` ne connaît pas les notes. Sans JavaScript, le bouton est un lien vers le formulaire de la note du jour. Le plan n'est lu qu'à l'ouverture (GET avec `HX-Request`), aucune page ne lit la note pour le dialogue. `note_taking/quick_capture.py` fait le texte : `targets` (les titres, comme `renaming.headings`, avec une clé faite du chemin et du rang, qui tient si la note change ailleurs), `add_to_body` (place, lignes vides, fins de ligne gardées). La ligne va **en fin du texte propre** du titre choisi, avant ses sous-titres (sinon elle changerait de chemin) ; sans titre, en tête de note, sans projet. `last_place` ne la met ni dans un bloc de code, ni dans un bloc `:::` ouvert dans la section, et ne sort pas de celui qui contient le titre. Un nouveau titre (suggestions de #90) va en fin de branche, ou reprend celui de même nom ; il est refusé si un bloc n'est pas fermé. Un texte qui ouvrirait un titre ou un bloc est refusé. `capture` écrit la note et recalcule ses passages en une transaction : en cas d'erreur, rien n'est écrit et le texte reste dans le dialogue. Le compte rendu est un toast (lien vers la note, et vers le bilan si c'est une tâche), sans redirection. Dans l'éditeur de la note du jour, le dialogue invite à y écrire.
- **Note changée depuis l'ouverture de l'éditeur** (#386) : le formulaire envoie `version`, la date de modification (`Note.updated`) à l'ouverture. Si elle n'est plus celle de la base, `edit_note` répond 409 sans rien écrire : la page revient avec le texte saisi, ou, sur place (#389), un toast et l'en-tête `X-Note-Version`. Un encadré propose de voir la version enregistrée et de la remplacer (`overwrite`, qui porte la version vue : une note qui change encore est de nouveau refusée). Un enregistrement sur place réussi renvoie la nouvelle version dans `X-Note-Version` ; si elle manque (page et serveur dépareillés après une mise à jour, #469), un toast demande de recharger la page. Le formulaire est en `autocomplete="off"` : un navigateur qui rendrait l'ancien texte au rechargement, avec la version neuve, tromperait le contrôle. Sans `version`, pas de contrôle.
- **Conflit expliqué** (#468) : `edit_conflict.conflict_reason` dit ce qui a modifié la note en dernier (`Note.updated_by`) et quand, et l'heure de la version dont part l'éditeur (la date si ce n'est pas aujourd'hui, les secondes dans la même minute). La phrase est dans l'encadré, ou dans l'en-tête `X-Note-Conflict` (encodé, sur place). Une version illisible ou pas plus ancienne que celle de la base est dite « sans modification connue » : c'est peut-être un bug. Le conflit est tracé en `WARNING`. L'éditeur est en `never_cache` : revenir par Précédent redemande la page, avec le texte et la version à jour.
- **Différences dans l'encadré** (#471) : le formulaire garde le texte de la note tel que l'éditeur l'a ouvert (`<textarea name="original" hidden>`, rien en base) ; `note_form.js` le remplace par le texte envoyé après chaque enregistrement sur place. En cas de conflit, `text_merge.describe_changes` compare ce texte à la version enregistrée, ligne à ligne (`difflib`, fins de ligne Windows ramenées à `\n`) : chaque endroit changé, sous ses titres (« P › R », titres des blocs de code exclus, « Avant le premier titre » sinon), avec ses lignes ajoutées et retirées ; les lignes vides ne comptent pas. Le texte est échappé par le gabarit (`note/conflict_changes.html`) ; sur place, la réponse 409 le porte dans un `<template data-conflict-changes>`, que le script recopie dans l'encadré. Sans texte d'origine (page ouverte avant cette version), l'encadré reste celui de #468.
- **Fusion automatique** (#472) : avant de refuser, `edit_note` tente `text_merge.merge_texts(original, texte saisi, version enregistrée)` (`mergeable`). Les deux séries de changements, calculées ligne à ligne depuis le texte d'origine, ne doivent pas se toucher : deux changements sur les mêmes lignes, sur des lignes voisines, deux ajouts au même endroit, ou deux fois le même changement, sont un conflit (règle prudente : rien n'est tranché ligne à ligne). Le résultat applique les deux séries au texte d'origine : chaque ligne vient du texte saisi ou de la version enregistrée, et le texte d'origine, envoyé par la page, ne peut rien faire écrire d'autre (au pire, il fait un conflit, ou retire une ligne que le texte saisi n'a pas). Ni fusion sans texte d'origine, ni pour « Remplacer par mon texte », ni pour un formulaire refusé. La note est enregistrée avec la source `merge` (`Note.Source.MERGE`), la fusion tracée en `INFO`, le toast nomme ce qui avait modifié la note (`edit_conflict.merge_message`) ; passages et tâches sont recalculés comme à tout enregistrement. Fins de ligne : celles du texte saisi. **Sur place**, la réponse (`note/save_toasts.html`) porte en `json_script` (`#note-merge`) le texte fusionné et les lignes venues d'ailleurs, en lignes du texte envoyé (`edits` : `from`, `to` exclue, `lines`). `note_form.js` les passe à l'éditeur (évènement `note:merge`) ; `merge.js` les applique comme une modification CodeMirror (`ChangeSet`), ramenée sur ce qui a été tapé depuis l'envoi (`note:saving` marque le texte envoyé) : curseur, sélection et frappe en cours restent. Sans éditeur, le `<textarea>` prend le texte fusionné s'il n'a pas changé depuis l'envoi ; sinon la page garde la version d'avant et le demande de recharger : l'enregistrement suivant serait un conflit, jamais l'effacement des lignes venues d'ailleurs. Après la fusion, la version et le texte d'origine sont ceux de la note fusionnée.
- **Modifications tracées** (#468) : `Note.save(source=Note.Source.…)` est le **seul point d'écriture du texte** (un test refuse un `note.save()` sans source). Sans `source` (shell), la modification est de source inconnue, et l'ancienne source n'est pas gardée.
- **Enregistrer sans quitter l'éditeur** (#389) : l'en-tête a deux boutons reliés au formulaire. « Enregistrer la note » (et Ctrl+S) envoie `stay=1` ; « Terminer l'édition » envoie le formulaire sans, et mène comme avant à la note ou au bilan des tâches. Avec `stay`, dans l'éditeur d'une note existante (`data-save-in-place`) et la date inchangée, `note_form.js` envoie le formulaire par `fetch`, avec l'en-tête `HX-Request` : la vue répond par les toasts (`core/components/message_toasts.html`, statut 422 si le formulaire est refusé, et rien n'est enregistré), que `Toast.insert` ajoute à la page ; le texte envoyé devient la référence de l'avertissement avant de quitter. Sans JavaScript, ou pour une nouvelle note, ou une date changée (l'adresse de l'éditeur en dépend), le formulaire est envoyé normalement et `stay` ramène à l'éditeur de la note.

Cet arbre ne connaît pas les blocs `:::` : `blocks.js` écarte les titres des blocs que le rendu traite à part (callout, colonnes, figure en colonnes, métadonnées) et qui sont fermés, si bien que le plan est celui de la page (#423) ; un test garde ses motifs égaux à ceux du rendu. - **Plan en lecture et sections repliables** (#404) : la page d'une note a aussi son plan, **rendu par le serveur** (`note_taking/note_outline.py`, `outline_sections`), donc lisible sans JavaScript : un `<nav aria-label="Plan de la note">` à droite du texte, collant quand le texte défile, une liste de liens vers les ancres des titres (#201), retrait par niveau (`OutlineEntry.indent`). Le premier niveau est trouvé par `html.parser` (profondeur des balises, éléments vides compris). `note_reading.js` ajoute : le bouton « Plan » (cloné d'un `<template>`, comme dans l'éditeur ; **affiché par défaut**, l'état est celui du plan de l'éditeur, même clé de `localStorage` ; sur une fenêtre étroite, sous 64rem, il est fermé d'abord et s'ouvre **par-dessus la feuille**, en haut à droite, collant lui aussi, où qu'on soit dans la note : il se referme sur un titre choisi, un clic ailleurs ou Échap, et son état n'est pas gardé ; sans JavaScript, il reste au-dessus du texte) ; un bouton par titre de section qui **replie son contenu, comme un `<details>`** (`aria-expanded`, `aria-controls`, contenu en `hidden`, titre gardé : un `<summary>` ferait perdre leur rôle de titre aux lecteurs d'écran) ; aller à un titre (plan, lien, adresse) déplie les sections qui le cachent ; et **la section lue en évidence** dans le plan (`aria-current="location"`) : le dernier titre visible passé sous un seuil depuis le haut de `<main>`, ou le dernier titre visible quand la page est défilée jusqu'en bas. Rien n'est replié par le serveur, et le repli n'est pas gardé d'une visite à l'autre.
- **Note en feuille, actions toujours visibles** (#421) : sur la page d'une note, l'en-tête blanc (titre sur une ligne, boutons) est en `sticky` en haut de `<main>`, qui reste la seule zone qui défile ; le plan se place dessous, et `scroll-pt` sur `<main>` (bloc `main_class` du gabarit de base) arrête toute ancre (titre, figure, tableau) sous l'en-tête. Le décalage d'un élément collant part de la marge intérieure de `<main>` : l'en-tête, qui la couvre, est à `-top-4`. L'échelle s'arrête à 0,7 (texte de 11,2 px) : en dessous, ou sans JavaScript, les marges se réduisent puis les lignes se recomposent. La place de la barre de défilement est réservée (`scrollbar-gutter`), sans quoi elle ferait osciller l'échelle. **La page ne défile pas de côté** : un tableau (dans un `<div class="table-scroll">` posé par `scrollable_tables` après le filtrage, donc aussi dans la recherche), un bloc de code ou une formule trop larges défilent seuls, et un mot trop long se coupe. Feuille et plan sont centrés ensemble. À l'impression, ni fond, ni ombre, ni marges, ni plan.

- **Listes de suggestions** (#90) : trois vues JSON en lecture seule, que l'éditeur interroge pendant la frappe. `core:project_suggestions` (`/projects/suggestions/?q=`, nom et couleur), `core:section_suggestions` (`/paths/suggestions/?project=&path=&q=` ; `path` s'écrit avec « / » comme à la saisie d'une tâche) qui renvoie deux listes : `results`, les niveaux sous ce chemin du projet nommé (les premiers niveaux si `path` est vide, rien si le projet ou un niveau n'existe pas), et `elsewhere`, les noms de niveau de **tous les projets et de tous les rangs** avec leur chemin d'origine (`where` : « PDS1 › Autre › Bilan », « (+2) » s'il y en a d'autres), une fois chacun (casse et accents ignorés ; on propose la graphie que portent le plus de niveaux, puis celle qui sert le plus en passages et tâches, puis l'ordre alphabétique, avec le chemin de son niveau le plus utilisé, #377), sans ceux déjà dans `results`, et **seulement quand `q` n'est pas vide** (sinon la liste de toute la base noierait l'autre) et `note_taking:image_suggestions` (`/images/suggestions/?q=`, nom, référence `images/<nom>` à écrire et adresse de la vignette). Les projets et chemins sont dans `core` (`core/suggestions.py`), qui ne connaît pas les notes ; les images dans `note_taking`, qui référence les images. - **Suggestions dans le texte** (#91, #92) : `suggestions.js` (module `@codemirror/autocomplete`, ajouté à `packages.json`) interroge ces trois listes pendant la frappe, par les adresses portées par le formulaire (`data-projects-url`, `data-sections-url`, `data-images-url`) ; après `](`, les notes, les plus récentes d'abord (`data-notes-url`, `note_suggestions`, #206).

Les tags à plat des blocs `{.metadata}` ne sont pas proposés : un titre crée un niveau, pas un tag.

- **Listes** (#320) : `lists.js`, dont la règle est écrite à la main parce que `@codemirror/lang-markdown` n'est pas embarqué. Entrée à la fin d'un élément (`- `, `* `, `+ `, `1. `, `2) `) crée l'élément suivant, de même retrait et de même marqueur (numéro suivant) ; sur une case (`- [x] a`, `- [ ] a`), la suivante est une case **vide** ; sur un élément **vide**, le marqueur disparaît (on sort de la liste) ; au milieu d'un élément, le texte à droite passe dans le nouveau. L'élément est reconnu par l'analyseur (`ListMark` de `@lezer/markdown`) : Entrée garde son comportement dans un bloc de code, une citation (`>`, pas continuée), un titre ou un trait horizontal, avec une sélection non vide, ou si le curseur est avant le texte de l'élément. Avec une liste de suggestions ouverte, Entrée n'accepte rien sans flèche (#91) : elle continue donc la liste. **Tab** et **Maj+Tab** (et Ctrl+] / Ctrl+[, peu pratiques sur un clavier français où `]` demande AltGr) indentent et désindentent les éléments sélectionnés **selon la règle de Pandoc** (#229) : une sous-liste commence à la colonne du texte de l'élément au-dessus (2 espaces sous `- `, 3 sous `1. `, 4 sous `10. `), alors que le retrait par défaut de CodeMirror (2 espaces) donnerait une sous-liste numérotée que Pandoc ne reconnaît pas ; hors liste, le retrait ordinaire s'applique. **Un élément ne s'imbrique que sous l'élément précédent du même niveau** (autant de niveaux qu'on veut : 4 espaces de plus que le texte du parent donneraient un bloc de code) : Tab sur un premier élément, ou sur un élément déjà imbriqué sans frère au-dessus, ne fait rien. Maj+Tab désindente d'un niveau, et ramène à la colonne du texte de son parent un élément déjà devenu bloc de code (seulement s'il a un parent : sans lui, c'est du vrai code indenté et rien ne change). **Les numéros suivent le déplacement** : un élément numéroté qui ouvre une sous-liste repart à `1.` (Pandoc commence une liste au numéro de son premier élément : un `2.` imbriqué ferait partir la sous-liste à 2), un élément qui rejoint une liste existante prend le numéro suivant, et un élément désindenté prend celui qui suit son parent ; seuls les éléments du niveau déplacé sont renumérotés. **Le style suit aussi (#419)** : ces éléments prennent le marqueur (type, casse, séparateur, espaces) du niveau où ils arrivent (`levelModel`) : le style majoritaire parmi leurs nouveaux frères, au-dessus et en dessous ; à égalité, celui du plus proche en nombre d'éléments, au-dessus d'abord. Un niveau vide leur laisse leur style ; les `(@)` gardent leur marqueur et ne comptent pas. **L'élément emmène ses suites et ses sous-listes**, même hors de la sélection, alignées sur son texte si la largeur du marqueur change ; ce qui le suivait dans son parent, et devient sa suite par Maj+Tab, s'y aligne aussi. **Marqueurs de Pandoc (#325)** : `parseMarker` est le pendant JavaScript de `parse_marker` (`qmd/lists.py`) et reconnaît les puces, `1.` `1)` `(1)`, les lettres, les chiffres romains, `#.` et `(@)`, avec les mêmes règles (une seule lettre, deux espaces pour `A.`, le contexte de la liste pour `i.` ou `v.`). Entrée continue avec le marqueur **suivant dans la liste** : `b.`, `ii.`, `(b)`, `B.  `, `2)` ; `#.` reste `#.`, `(@étiquette)` donne `(@)`, et `z.` reste `z.`. Tab et Maj+Tab renumérotent le niveau déplacé : `a.` et `i.` repartent de `a` et `i` quand l'élément ouvre une sous-liste, `(a)` s'indente de 4 espaces, `A.` garde ses deux espaces (`III.` devient `I.  `). L'analyseur de @lezer/markdown ne connaît que les puces, `1.` et `1)` : pour les autres marqueurs, et pour les lignes sous eux (#417), une ligne est un élément si le rendu en fait un. Son niveau est donné par `scanLists`, pendant de `PandocListsPreprocessor` (`rendering/lists.py`) : les éléments ouverts dont la ligne atteint la colonne du texte ; Tab et Maj+Tab s'y fient pour toutes les listes. Tab n'est détourné **que dans une liste** (avec une suggestion ouverte, il la complète d'abord) : sur une autre ligne, dans un bloc de code ou sur un titre, il passe au champ suivant. Maj+Tab sur un élément sans retrait ne fait rien. Pour ne pas piéger le clavier, **Échap puis Tab** (ou Ctrl+M) quitte l'éditeur même dans une liste : CodeMirror laisse alors passer Tab ; l'aide de l'éditeur le rappelle. Un Échap pressé pendant que la liste de suggestions s'ouvre sert d'abord à la fermer.
- **Marqueurs des listes de Pandoc** (#328) : `a.`, `A)`, `(1)`, `iv)`, `#.`, `(@)` sont des paragraphes pour l'analyseur. `pandocListMarks` (`lists.js`, un `ViewPlugin` de décorations sur les lignes visibles) colore leur marqueur comme les `ListMark` (`cm-pandoc-list-mark`, `amber-700`), d'après la règle de `itemOf` (après une ligne vide, un titre ou dans une liste, jamais collé à un paragraphe, hors code et citations). **Sous un tel marqueur** (#417), l'arbre place mal les `-` et `1.` (pour lui, `A.  x` est la suite du texte) : leur couleur suit la même règle, celle du rendu, et non `ListMark`. **Coloration seule**, choix de l'utilisateur : l'analyseur n'est pas étendu, l'arbre syntaxique ne contient toujours pas ces listes, et `lists.js` garde `scanLists` et `knownToParser`. Étendre l'analyseur (`MarkdownConfig`) reste possible si le plan ou un repli doivent un jour lire ces listes.
- **Retrait suspendu** (#418, `hanging.js`) : la suite d'une ligne trop longue revient sous son texte. Une décoration de ligne pose `padding-left` et un `text-indent` négatif égaux à la colonne du texte, en `ch` : pour un élément de liste, celle de l'imbrication (`itemOf`, case à cocher comprise) ; pour une citation, le texte après ses `>` (et le marqueur d'une liste qui s'y trouve) ; pour une autre ligne indentée, son retrait. Quarante colonnes au plus, pour laisser de la place dans une fenêtre étroite. Ce qui précède le texte et son premier caractère ne se séparent pas (`cm-hanging-prefix`) : devant un mot trop long, le marqueur resterait sinon seul sur sa ligne. Pas de pourcentage : CodeMirror lit ce `text-indent` en pixels pour dessiner la sélection. Une tabulation dans ce retrait laisse la ligne telle quelle.
- **Tableaux** (#401, `tables.js`) : l'analyseur a l'extension `Table` de `@lezer/markdown`, donc les tableaux à barres (`| a | b |`, pipe tables de Pandoc) sont des nœuds `Table` ; un tableau dans un bloc de code n'en est pas un. Les tableaux en grille (`+---+`) ne sont pas reconnus. **Formater** (`formatTable`, `formatTables`) : chaque cellule prend la largeur de la plus large de sa colonne, comptée en caractères affichés (`displayWidth` : un caractère perçu, `Intl.Segmenter`, compte pour 1, un caractère chinois, japonais, coréen, pleine chasse ou un emoji pour 2) ; alignements `:---:` gardés (et appliqués au remplissage), cellules manquantes ajoutées vides, `\|` respecté, retrait de la première ligne repris, colonnes d'au moins 3. Une seule modification, donc un seul Ctrl+Z ; le curseur reste à sa place dans le texte ; le rendu ne change pas. Un tableau à barres n'a qu'une ligne par cellule : la « hauteur » de #401 ne s'applique pas. Les lignes d'un tableau **reviennent à la ligne** comme le reste du texte (#436) : sans retour (#402), un tableau large faisait défiler tout l'éditeur ; il s'édite plutôt dans une fenêtre à part.
- **Menu du clic droit** (#400, #437, `editor_menu.js`) : le clic droit ouvre notre menu à la place de celui du navigateur ; **Maj + clic droit** garde celui du navigateur (correcteur orthographique), ce que rappelle la dernière ligne du menu et l'aide sous l'éditeur. Le curseur vient au point cliqué, sauf dans la sélection. Au clavier, **Maj+F10** et la touche Menu l'ouvrent au curseur ; flèches (en boucle, entrées grisées sautées), Début, Fin ; flèche droite ou Entrée ouvre un sous-menu, flèche gauche le ferme ; Échap ferme tout et rend le focus à l'éditeur, Tab et un clic à côté ferment. **Une seule liste décrit le menu** (`entries` : libellé, raccourci affiché, condition d'affichage, entrée grisée, action ou sous-menu) : une issue y ajoute ses entrées sans toucher au reste, qui est la mécanique (`buildPanel`, `openSubmenu`). Entrées : **Couper**, **Copier** (grisés sans sélection, par les commandes du navigateur, où CodeMirror met sa sélection), **Coller** (`navigator.clipboard.read` : une image par le chemin des captures, #196, sinon le texte ; un refus du navigateur dit d'utiliser Ctrl+V) ; **Insérer** : image existante (écrit `![` et ouvre la liste des images, #92), importer une image, et les **blocs** de `block_templates.js` (#420) : tableau, callout, formule, colonnes, figure en colonnes, métadonnées, légende de tableau, renvoi. **Une seule liste des blocs** (`blockTemplates` : libellé, squelette, nombres à choisir) : un nouveau bloc du rendu y prend une ligne, et un test rend chaque squelette. Un bloc va sur ses propres lignes, séparé par des lignes vides, après le tableau si le curseur est dans un tableau ; une sélection est enveloppée par un callout (lignes entières si elle en touche plusieurs) ou une formule ; une seule modification, donc un seul Ctrl+Z. Les types de callout, leur titre et leur icône viennent du rendu : la balise `callout_templates` (`editor_tags.py`) en écrit un `<template>` chacun, que le menu clone ; **Tableau**, seulement si le clic tombe dans un tableau ; et le formatage groupé. Le menu est construit par le script (classes Tailwind dans le fichier, détectées par la compilation) : sans JavaScript, il n'y a ni éditeur ni menu.
- **Formatage groupé des tableaux** (#437, `tables.js`) : « Formater les N tableaux de la sélection » (ceux qu'elle touche, même en partie), sinon « Formater tous les tableaux (N) », grisé s'il n'y en a pas. `findTables` lit l'arbre de **toute** la note (`ensureSyntaxTree`), pas de la partie visible, et laisse de côté ce que `formatTable` ne reconnaît pas. `formatTables` fait **une seule modification** (un Ctrl+Z annule tout), réduite aux espaces et aux barres (`rowChanges`) : le texte des cellules n'est pas touché, donc curseur et sélection y restent. « Formater le tableau » passe par là aussi. Les cellules sont découpées comme le rendu (`splitTable`, d'après `TableProcessor`) : `\|` et une barre dans du code ne séparent rien. Une légende ou un `:::` collés sous le tableau, que l'analyseur prend pour une ligne, n'en sont pas (`lastRow`) ; un tableau sur la ligne d'une puce ou dans une citation n'est pas touché.
- **Lignes et colonnes d'un tableau** (#435, `table_edit.js`) : le sous-menu « Tableau » insère (avant, après) et supprime la ligne ou la colonne de la cellule cliquée, et change les dimensions (« Dimensions… », le formulaire de l'insertion, `countsForm`). Une **commande** est une fonction pure sur les cellules (`insertRowAfter`, `deleteColumn`, `resizeTable`…), `null` si elle est impossible (entrée grisée : rien avant l'en-tête, ni suppression de l'en-tête, de la séparation ou de l'unique colonne) ; `editTable` l'applique à un texte, `runTableCommand` à l'éditeur, sans dépendre du menu. Le tableau sort formaté, en **une seule modification** et sans confirmation : un Ctrl+Z l'annule. Une ligne plus longue que l'en-tête élargit le tableau (le rendu cachait ses cellules en trop).
- **Tableau dans une fenêtre à part** (#436, `table_dialog.js`) : « Éditer le tableau… », en tête du sous-menu « Tableau », ouvre le tableau seul dans un `<dialog>` modal presque plein écran, cloné d'un `<template>` du gabarit, avec un second CodeMirror **sans retour à la ligne**. `createEditor` (`editor.js`) crée les deux éditeurs : `own`, ce qu'ils ne partagent pas (retour à la ligne, retrait suspendu et listes pour la note ; sans les listes, Tab mène aux boutons). Le texte est le tableau **et sa légende** (`tableBlocks`, les règles du rendu : celle d'avant l'emporte, une légende n'est prise qu'une fois), sans son retrait dans une liste, remis à la validation. Valider (Ctrl+Entrée) remplace ces lignes en une seule modification ; si elles ne sont plus dans la note telles qu'à l'ouverture, rien n'est remplacé et la fenêtre reste ouverte ; un texte qui n'est plus un tableau est mis quand même, avec un toast. Échap et « Annuler » ferment ; avec des modifications, la popover `.confirm-popover` demande confirmation. Échap est géré au clavier et non par l'événement `cancel`, que Chrome rend impossible à refuser à la deuxième fois. `beforeunload` protège ce qui n'est pas validé ; Ctrl+S n'enregistre pas la note et le dit. Dans la couche supérieure, le reste de la page est inerte : le menu du clic droit s'ajoute à la fenêtre et `#toasts` y vient tant qu'elle est ouverte.
- **Paires et mise en forme** (#434, `formatting.js`) : `closeBrackets` de CodeMirror sur `()`, `[]`, `{}`, `''`, `""` et `` ` `` (ni `*` ni `$`) ; le fermant tapé devant lui-même est sauté, Retour arrière supprime une paire vide, une sélection est entourée, même dans une formule ou un bloc de code (#498). Sans sélection, rien dans un bloc de code délimité ni dans une formule, que l'analyseur ne connaît pas (`inMath`, règles du rendu) ; un bloc indenté garde les paires, l'analyseur en voyant dans des listes de Pandoc. Pas de paire pour une apostrophe après une lettre ; un deuxième `"` ou `` ` `` de la ligne ferme, le troisième accent grave ouvre un bloc. **`$` sur une sélection** (#498, `wrapInMath`, un `inputHandler`) la met en formule : `$…$` sur une ligne, les blancs des bords laissés dehors (Pandoc n'en veut pas juste à l'intérieur) ; sur plusieurs lignes, `$$` sur une ligne au-dessus et une en dessous, au retrait de la première ligne (la formule reste dans son élément de liste) ; chaque sélection, en une annulation. Sans sélection, `$` s'écrit seul (montants, formules tapées), et il s'écrit aussi tel quel dans un bloc de code ou une formule. Une suggestion acceptée remplace le fermant ajouté (`to` des sources de `suggestions.js` : `closedImageEnd` pour `![`, la fin de la ligne d'un titre). **Ctrl+B, Ctrl+I, Ctrl+U** (et « Mise en forme » du menu) sont des bascules, en une annulation : sur la sélection, ligne par ligne et sans les marqueurs (une mise en forme ne passe pas d'un élément à l'autre), sinon le mot du curseur, sinon une paire vide ; dans un texte déjà mis en forme, toutes ses marques sont retirées. Placés avant les raccourcis de CodeMirror, où Ctrl+I et Ctrl+U sélectionnent le nœud parent et annulent une sélection.
- **Coller ou déposer une capture** (#196) : dans l'éditeur, une image du presse-papiers (Ctrl+V) ou déposée (glisser-déposer) est envoyée à `note_taking:image_capture` (`/images/capture/`, POST), puis `![](images/nom)` est inséré à la position du curseur, qui se place après (une autre capture vient à la suite). Pendant un glisser-déposer, un trait vertical bleu (`dropCursor()`) marque l'endroit où l'image s'insérera ; pour un collage, c'est le curseur de texte. Le texte collé n'est pas concerné : seul un fichier image est intercepté. `note_taking/captures.py` donne le nom (`capture-AAAA-MM-JJ-HHMMSS.png`, suivi de `-2`, `-3`… si pris ; l'extension vient du type MIME, svg compris) puis réutilise `images.services.import_image`, qui vérifie le contenu : `images` ne connaît toujours pas les notes. Un refus (contenu qui n'est pas une image, type inconnu) est une erreur métier : réponse 400 `{"error": …}`, affichée en toast, texte inchangé. Sur la page des images, `images_capture.js` fait de même sur toute la page, puis la recharge ; le champ `notify` demande au serveur de laisser le message de succès ou de refus pour ce rechargement (dans l'éditeur, pas de message : le toast suffit). Le jeton CSRF vient du formulaire (éditeur) ou de la page.

### Analyse des notes

Les règles d'analyse sont décrites dans le README. Choix notables :

- le texte placé avant le premier projet (`#`) est un passage sans projet (#385, avant ignoré, #36) : cherchable, ses images liées, ses cases des tâches à ranger, et l'enregistrement le rappelle (premier de `note.warnings`, pour que le message « N autres titres à vérifier » ne compte que des titres) ;
- les callouts Quarto sont conservés dans le contenu et rendus en encadrés à la manière de Quarto (#39) ;
- l'indentation du contenu est conservée (#34).

### Erreurs métier

`core.exceptions.AppError` est la base des erreurs dont le message est destiné à l'utilisateur (`NoteError`, `ImageError` et leurs sous-classes). Les vues n'attrapent que celles-ci ; toute autre exception est un bug et n'est pas masquée. Un import de plusieurs fichiers traite chaque fichier indépendamment, en tout ou rien.

### Champs texte

Aucun champ texte n'est nullable : chaîne vide par défaut (#48, règle ruff `DJ001`).

### Composants d'interface (#78)

Les éléments d'interface récurrents (boutons, liens du menu, listes de tags…) sont des composants partagés, définis une fois dans `core` :

- **Mécanisme** : des balises d'inclusion Django (`inclusion_tag`) dans `core/templatetags/ui.py`, chargées avec `{% load ui %}`. Chaque balise prépare le contexte et rend son gabarit, dans `core/templates/core/components/`. Elles ont été préférées aux `{% include … with … %}` : l'appel est plus court, les paramètres sont nommés et vérifiés (un paramètre inconnu est une erreur de gabarit), et une valeur invalide, comme une variante qui n'existe pas, peut être refusée.
- **Un composant par rôle, pas par apparence** : deux éléments qui se comportent de la même façon pour l'utilisateur sont un seul composant. Par exemple, `button` rend un `<a>` quand on lui donne un `href` et un `<button>` sinon : la balise HTML découle de l'action (naviguer ou envoyer un formulaire), elle n'est pas un choix à faire à chaque appel. Un composant à part se justifie par un comportement propre : `nav_link` calcule lui-même son état actif à partir de la page courante.
- **L'apparence passe par `variant`** (`primary`, `danger`, `ghost`…). Les classes Tailwind de chaque variante sont écrites en entier, dans le gabarit ou dans un dictionnaire de `ui.py`, jamais construites par morceaux.
- **Une API minimale** : peu de paramètres, avec des valeurs par défaut qui couvrent l'usage courant. Le libellé est le premier argument, positionnel ; tout le reste est nommé. Un paramètre ou une variante ne s'ajoute que lorsqu'une page en a besoin, pas par anticipation.
- **Accessibilité intégrée** : un élément réduit à une icône reçoit son libellé en `aria-label`, et le lien de menu actif reçoit `aria-current="page"`. Le gabarit de base nomme le menu (`<nav aria-label="Menu principal">`) et commence par un lien d'évitement « Aller au contenu » vers `<main id="contenu">`, masqué hors focus (#191).
- **Confirmation** (#292) : `confirm_button` est un composant à part parce qu'il a un comportement propre : bouton de la page + popover native (`popover`, `popovertarget`) qui contient le message et le formulaire POST. Le navigateur gère ouverture, fermeture (Échap, clic à côté, « Annuler »), focus et `aria-expanded`, sans JavaScript ; le placement sous le bouton vient de l'ancrage CSS (`.confirm-popover`, `position-area`, `flip-block`), sans lui la popover est centrée. Un bouton désactivé (suppression impossible) est rendu seul, relié à sa raison. Le texte du message est préparé par la vue ou le gabarit (`TreeRow.delete_confirm`, `delete_confirm`), pas par le composant ; il **n'y met pas le nom de l'objet** (titre de tâche, nom de projet, de niveau ou d'image : possiblement très longs, et déjà sous les yeux), seulement ce qui part avec lui ; la date d'une note, courte et sûre, y reste. La popover a `overflow-visible` (sans quoi `[popover]` défile par défaut) et `break-words [overflow-wrap:anywhere]` : jamais de barre de défilement, la hauteur s'adapte.
- **Toasts** (#293) : repris de research-paper-relationship-graph. `{% message_toast message %}` rend un message Django en HTML (`core/components/toast.html`, variante et icône selon le niveau, `role="alert"` pour une erreur, `status` sinon) ; il est donc **visible sans JavaScript**, où il reste affiché. `core/static/core/toasts.js`, chargé par le gabarit de base, ajoute le bouton de fermeture (caché sans script), la touche Échap et la disparition des seuls succès et informations après 6 s, en pause tant que le pointeur ou le focus est sur le toast. Les toasts sont dans `#toasts`, en bas à droite. Un script crée un toast par `Toast.show(message, "error" | "success")` : clone du `<template id="toast-template-…">` rendu par `{% toast_template %}`, message placé en texte, jamais lu comme du HTML. Les classes de gris sont en `slate`, la famille des gris de l'app. L'ancien système de toasts créés en JavaScript (titre, barre de progression, 5 s pour tous) est supprimé.
- **Espaces insécables** (#383) : le filtre `nbsp_punct` de `ui` (`core/typography.py`) remplace l'espace écrite avant `;`, `:`, `!`, `?` et `»`, et après `«`, par une espace insécable (U+00A0), pour que la ligne ne se coupe pas devant la ponctuation ; il n'en ajoute pas là où il n'y en a pas (« 10:30 », `chemin:`), réduit plusieurs espaces à une et garde une insécable déjà là. Plutôt que de corriger chaque chaîne, il s'applique au rendu : texte des toasts (`toast.html`, donc tous les messages Django), message de `confirm_button`, libellé affiché de `button`, erreurs et aides des formulaires en grille (`core/forms/grid.html`), et titres des gabarits écrits avec des guillemets (`{% filter nbsp_punct %}…{% endfilter %}`). `Toast.show` (`toasts.js`) applique la même règle. Un texte ordinaire est échappé puis modifié ; un HTML déjà sûr n'est modifié qu'entre les balises, sans toucher à `<code>`, `<kbd>`, `<pre>`, `<textarea>`. Il ne s'applique ni au contenu des notes (Markdown rendu), ni aux valeurs des champs, ni aux attributs.
- **Arbre des chemins** (#302) : un seul composant pour tous les usages (filtre de la recherche, filtre de niveau des tâches, arbre de la fiche projet), modèle `tag_tree` de research-paper-relationship-graph. `core/path_tree.py` construit les nœuds (`path_tree(counts, selected, project, only_counted)` : une requête, liste à plat parents d'abord, frères triés sans casse, chaque `PathNode` a aussi ses `children`), la balise `{% path_tree nodes mode=… param=… %}` (`ui.py`, gabarits `path_tree*.html`) les affiche. **`core` ne connaît aucune app** : l'appelant fournit `counts`, un dictionnaire « clé d'un niveau → ce qui l'utilise lui-même » ; le compteur d'un nœud y ajoute ses descendants, comme filtrer sur un niveau les inclut. Sans `project`, chaque projet qui a des niveaux est un nœud de profondeur 0 (ni lien ni case, sauf en mode `checkbox` avec `project_param` : une case `name=project_param`, qui prend les projets sans niveau si l'appelant passe `project_counts`, et `selected_projects` pour les cochés) et le chemin complet « Projet › A › B » est le `label` (infobulle) ; avec `project`, seuls ses niveaux, sans nœud de projet. `only_counted` ne garde que les niveaux utilisés ou choisis, avec leurs parents. Deux modes : `link` (lien vers la page courante avec `?param=<clé>`, le reste de la requête gardé et `page` retiré ; le niveau choisi est marqué `aria-current="true"` et son lien retire le filtre) et `checkbox` (une case `name=param`, dans un formulaire de l'appelant). **Sans JavaScript** : listes `<ul>` imbriquées, un `<details>` natif par niveau qui a des sous-niveaux, ouvert d'office quand un descendant est choisi (le niveau choisi lui-même reste replié) ; le chevron ne regarde que son propre `<details>` (`[details[open]>summary>&]:rotate-90`, pas `group-open` qui hériterait de l'état des parents) ; le compteur s'affiche s'il n'est pas nul ; `count_noun` (« passage ») le nomme au survol et pour les lecteurs d'écran (#362). La recherche (M15), le filtre de la liste des tâches et la fiche projet (#205) s'en servent.
- **Cases de l'arbre des chemins** (#433, `core/static/core/path_tree.js`, partout où l'arbre est en cases, `data-path-tree`) : l'arbre montre ce qui est cherché. Sous un niveau coché, les cases sont cochées et grisées (donc pas envoyées), avec l'info-bulle « Compris dans … » ; au-dessus, elles sont `indeterminate`. Décocher rend aux sous-niveaux leur état d'avant, gardé sur la case (`data-own`). Le script écoute en phase de capture, pour que htmx et `saved_searches.js` lisent des cases à jour ; tout est recalculé après un retour en arrière (`pageshow`, `htmx:historyRestore`). Côté serveur, `path_tree` ne choisit pas un niveau compris dans un niveau ou un projet choisi : il n'est ni coché, ni une puce des filtres d'un tableau (`PathTreeFilter.read`). Sans JavaScript, toutes les cases restent actives et le résultat est le même.
- **Sélection du contenu seul** (#497) : une sélection à la souris ou par Ctrl+A, collée ailleurs, n'emporte que le contenu. Les règles sont dans les styles de base (`assets/css/source.css`) plutôt que sur chaque élément, pour couvrir aussi ce que créent les scripts (repli des sections, menu de l'éditeur, « Copier le chemin ») : `nav` (menu, plan de la note et de l'éditeur, barres de présentation, fil du chemin d'un résultat, mois et semaine), `button`, `[role="button"]`, `summary`, `kbd`, `::placeholder` (le « Rechercher… » de la barre était copié), `::file-selector-button` et `.sr-only` (texte pour lecteurs d'écran, invisible). Les champs (`input`, `textarea`, `[contenteditable]`, donc l'éditeur) restent sélectionnables, même dans une zone qui ne l'est pas. En plus : `select-none` dans `BUTTON_SHAPE` (un lien-bouton `<a>`), sur l'en-tête général, le lien d'évitement et les compteurs (« 20 passages dans 12 notes »). Restent sélectionnables : le contenu des notes et des tâches, les titres de page, les tags, les toasts (un message d'erreur se copie), les numéros des figures et tableaux (« Figure 1: », comme dans Quarto, et repris par les renvois) et les en-têtes de colonnes des tableaux, utiles quand on copie un tableau.
- **Tests** : chaque composant a des tests du HTML rendu (`core/tests/test_components.py`), qui servent aussi de référence pour ses classes.

## Conventions de travail

### Tests

- `python manage.py test` ; tests dans un paquet `tests/` par app.
- **Tests d'abord** : avant de modifier un comportement, un commit ajoute les tests du comportement attendu, marqués `@unittest.expectedFailure` ; le commit de correction retire le décorateur.
- **Élagage en fin de milestone** : une issue, traitée en dernier, repasse sur les tests ajoutés pendant le milestone. Elle supprime les tests d'absence d'une chose retirée qui n'a pas de raison de revenir (un bouton, un panneau), garde ceux qui protègent une règle transversale ou une faille (ils échoueraient si un nouveau gabarit l'enfreignait), et fusionne les tests redondants.
- Le parseur est couvert par une note d'exemple (`note_taking/tests/data/exemple.qmd`) dont le résultat attendu est figé (`exemple.json`, régénérable avec `UPDATE_GOLDEN=1`, diff à relire).

### Outillage et CI

- `ruff` (lint et formatage, configuration dans `pyproject.toml`), `mypy` avec `django-stubs` (`mypy.ini`).
- `djlint` vérifie les gabarits (`djlint --lint`, configuration dans `pyproject.toml`, quelques codes ignorés par fichier avec leur raison). Son formatage automatique n'est pas utilisé : il coupe les attributs et ajoute des espaces dans le HTML produit (titres d'onglet, éléments en ligne), ce que les tests et le rendu remarquent (#242).
- `coverage` mesure la couverture des tests, sans seuil bloquant (`coverage run manage.py test`, puis `coverage report`).
- La CI GitHub Actions lance `ruff check`, `ruff format --check`, `mypy`, `djlint --lint`, `makemigrations --check`, les tests avec la couverture (validation HTML comprise) et la construction de la feuille Tailwind à chaque PR.
- Dependabot (`.github/dependabot.yml`) propose chaque semaine les mises à jour des dépendances `pip` et des GitHub Actions, les mineures et correctives regroupées dans une seule PR.
- `main` est protégée : une PR ne peut être mergée que si la CI passe et que la branche est à jour.
- **Validation HTML** (#259) : le validateur du W3C (Nu Html Checker, `vnu.jar`) tourne **en local**, jamais en ligne, car le validateur en ligne recevrait le contenu des notes. `python manage.py install_validator` le télécharge (paquet npm `vnu-jar`, version et intégrité épinglées par `VNU_VERSION` et `VNU_INTEGRITY`) dans `.vnu/`, non versionné ; il demande Java. `core/tests/test_html_validation.py` valide alors les pages principales, rendues avec des données de test ; sans validateur, ce test est ignoré. La CI l'installe et le lance à chaque PR. La dernière issue d'un milestone qui touche au HTML vérifie qu'il passe et en étend la liste de pages si besoin.

### Git

- Une branche par issue, partie de `main` à jour ; pas de PR empilées.
- Messages au format Conventional Commits, en français (`type(portée): description`).
- Merge par merge commit (le commit de formatage est référencé dans `.git-blame-ignore-revs`).

### Migrations de données

- Une migration de données n'importe pas le code de l'application (les modèles et le parseur évoluent) : elle utilise `apps.get_model` et, si besoin, une copie figée des fonctions utiles.
- Elle échoue sans rien modifier si les données ne sont pas dans l'état attendu, plutôt que de perdre de l'information.
- Avant la PR, elle est vérifiée sur une **copie** de la base réelle (comparaison avant / après, en SQL).
- Avant de l'appliquer : sauvegarder `db.sqlite3`.
